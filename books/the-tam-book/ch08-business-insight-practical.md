## 8.1 业务地图绘制

### 银行业务地图（示例）

| 业务主线 | 核心功能 | 技术特点 | 峰值特征 |
|----------|----------|----------|----------|
| 核心系统 | 存、贷、汇 | 稳定压倒一切，变更窗口以月计 | 年终决算 |
| 渠道 | 手机银行、网银、柜面、开放银行 | 直接面对 C 端体验 | 营销活动、节假日 |
| 风控 | 信贷审批、反欺诈、反洗钱 | AI 渗透率高，数据时效性敏感 | 实时 |
| 监管报送 | 对监管机构的数据报送 | 死线刚性、口径刚性 | 季度/年度 |

### 证券、保险、支付业务地图

| 行业 | 主线 | 峰值特征 |
|------|------|----------|
| 证券 | 交易、行情、清算 | 行情日峰值与两市成交额强相关 |
| 保险 | 承保、理赔、开门红 | 开门红期间峰值高 |
| 支付 | 清算峰值、7×24 | 零容忍，任何时间都不能中断 |

### 操作步骤

1. **选择行业**：确定客户所属行业（银行/证券/保险/支付）。
2. **画出主线**：用思维导图或表格列出 3–5 条业务主线。
3. **标注技术依赖**：每条主线标注核心系统、依赖组件、关键接口。
4. **标注峰值特征**：每条主线的峰值时间、峰值系数、业务影响。
5. **验证**：与客户技术负责人确认地图准确性。

### 预期结果

同事 5 分钟看懂客户核心业务。主线带技术依赖。客户确认准确。

### 从地图到行动

地图不是墙上的装饰。它直接驱动三件事：

1. **容量与重保**：每条主线的峰值特征，是第 24 章重保立项与容量校核的输入；
2. **变更窗口**：主线峰值日历直接约束[附录 T](appx-t-online-change-standard.md)的窗口选择；
3. **风险排序**：影响主线越多的事件定级越高。定级口径见第 25 章。

画图也有边界。规划中的系统标注"规划"，不与在运系统混排。供应商内部工具不进图。除非客户业务直接依赖它。

### 地图保鲜三规则

- 系统上线或下线，两周内更新主线与依赖；
- 组织架构调整，同步更新关键接口；
- 每季度随服务计划刷新复核一次。

### 常见错误

- 地图只有系统清单，没有业务主线。
- 只有业务名称，没有技术依赖。
- 画完不更新。组织或系统变了图没变。

## 8.2 业务日历建立

### 业务日历模板

| 日期 | 节点类型 | 节点名称 | 技术动作 | T-30 动作 |
|------|----------|----------|----------|-----------|
| 12.31 | 刚性 | 年终决算 | 核心系统冻结 | 提前 30 天启动容量校核 |
| 6.30 | 刚性 | 半年度监管报送 | 数据校验 | 提前 30 天启动数据核对 |
| 11.11 | 弹性 | 双十一大促 | 容量扩容 | 提前 60 天启动扩容评估 |
| 每季度末 | 内部 | 供应商考核 | 服务报告 | 提前 15 天准备报告 |

### 操作步骤

1. **收集节点**：从客户处获取年度业务日历（通常由业务部发布）。
2. **分类标注**：标记刚性节点、弹性峰值、内部节奏。
3. **倒排动作**：每个节点倒排 T-30 的技术动作。
4. **建立台账**：与技术档案并列存放，每季度与客户接口人核对。
5. **动态更新**：节点变更时及时更新，确保日历最新。

### 客户没有现成日历时

多数客户拿不出一份现成日历。三步自己拼：

1. **问监管与财务**：监管报送节点看发文日历。决算节点看财务日历。这两类最刚性；
2. **问业务节奏**：营销节奏问渠道部门。开门红、大促、行情日从业务例会纪要里捞；
3. **拼完送确认**：自拼日历送客户接口人书面确认。确认过的日历才有约束力。

弹性节点允许改期。刚性节点改期必须留客户书面痕迹。

### 刚性与弹性的判定

分不清节点类型时，用两个问题判定：

1. **改期的代价是什么**？改不动、或要监管书面批准的，是刚性；
2. **峰值可预估吗**？可预估、可压降的是弹性。完全不可预估的另立专项。

判定留痕。每个节点在日历里写判定理由。季度核对时理由还在，口径就不漂。有争议的从高处理。按刚性准备了，弹性自然覆盖。

### 节点分级倒排表

| 提前量 | 刚性节点动作 | 弹性节点动作 |
| --- | --- | --- |
| T-60 | 容量评估启动 | 扩容评估启动 |
| T-30 | 专项体检、数据核对 | 压测与扩容执行 |
| T-7 | 冻结确认、值守排班 | 降级预案就位 |
| T+1 | 结果确认、复盘 | 释放资源、复盘 |

### 预期结果

刚性节点无遗漏。每个节点有倒排动作。日历与技术档案同址存放。

### 常见错误

- 只记大节点，漏掉内部节奏。
- 有频次没日期。动作倒排落空。
- 业务侧改期，日历不知道。

## 8.3 价值翻译操作

### 翻译公式

```
技术指标 → 业务影响 → 财务影响
```

### 翻译示例

停机换算按 365 天等比折算，读者可复算。右列金额用 X、Z 占位，代表客户自己的口径，不是行业数。

| 技术指标 | 业务影响 | 财务影响 |
|----------|----------|----------|
| 可用性 99.9% → 99.99% | 年停机 8.8 小时 → 53 分钟 | 避免 X 万笔交易失败及对应中收损失 |
| 平均修复时间（Mean Time To Repair，MTTR）45 → 15 分钟 | 每次故障少 30 分钟中断 | 单次故障损失降 2/3 |
| 容量扩容（85% → 55%） | 峰值期间不排队、不降级 | 大促多承载 Z 亿成交额 |

### 操作步骤

1. **选择指标**：从技术报告中选择一个关键指标。
2. **翻译业务影响**：用客户业务语言描述指标变化的意义。
3. **估算财务影响**：用客户认可的数据或行业公开口径估算。
4. **注明出处**：在报告里注明数据来源和假设。
5. **验证**：请客户确认翻译的准确性。

### 两个纪律

- **量化必须有出处**：交易单价、笔数都用客户认可的数据。或用行业公开口径。出处写进报告；
- **讲不清财务影响时，退而求其次讲风险影响**。

### 三个常用句式

- 对业务方：“这个指标的变化，意味着高峰期少损失多少笔交易。”
- 对管理层：“这笔投入买的是什么风险的下降。”
- 对财务：“按贵行口径测算，年化影响在什么量级。”

### 翻译自查三问

送出前自查三问：

1. 业务影响一句能说清吗？说不清说明还停在技术层；
2. 财务数字的出处客户认可吗？拍脑袋的数字不如不给；
3. 反向问一句：指标不变会怎样？答不出代价，说明影响没挖到。

AI 成本同样能翻。GPU 排队时长翻成模型上线延期。延期再翻成业务机会损失（第 27 章）。

### 翻译的三个禁区

有三类话不要出现在价值翻译里：

1. **没有时点的承诺**：“将大幅提升”没有时点与幅度。客户无法验证；
2. **不可比的对比**：拿不同口径的基线比较。金融客户一定查得出来；
3. **超出服务边界的功劳**：业务量增长归因于市场。技术只认可用性与效率改善。

踩中禁区的翻译比不翻译更伤。客户会把整份报告一起打折。

### 预期结果

每个指标都能译成业务影响。财务影响有出处。客户认可翻译准确。

### 常见错误

- 只翻到技术层面，没触及业务影响。
- 财务影响拍脑袋，没有出处。
- 翻译过于复杂，非技术人员看不懂。

## 8.4 目标挂靠验证

### 目标层次

```
公司战略 → 部门目标 → 项目目标 → 你的服务动作
```

### 操作步骤

1. **获取公司战略**：从客户年报或年度工作报告中提取。
2. **识别部门目标**：与客户接口人确认科技部的年度目标。
3. **挂接项目目标**：确认每个项目对部门目标的贡献。
4. **验证链条**：问客户“这个项目对部门今年的目标意味着什么？”
5. **标记风险**：挂不上的工作要警惕，可能是低优先级。

### 挂不上的处理

挂不上的项目分两类。低价值的，向客户明示优先级取舍。有风险的，说明不投入的后果。别硬挂。客户一旦识破硬挂，比不挂更伤可信度。

### 重新验证的三个触发

挂靠不是一次性的。三个触发出现即重验：

1. 客户年度战略或部门目标调整（年报、年度工作会议）；
2. 客户接口人或分管高层变动；
3. 项目范围发生重大变更。

重验只做一件事：把挂靠清单逐项再问一遍"还挂得住吗"。

### 预期结果

每个项目一句话说清挂靠目标。挂不上的项目 ≤ 10%。客户高层能复述业务价值。

### 常见错误

- 只关注项目交付，不问业务目标。
- 挂靠牵强，客户不认可。
- 目标变了不重新验证。

## 8.5 验收标准

| 验收项 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 业务地图 | 3–5 条主线带技术依赖，客户确认 | 抽查地图与确认记录 |
| 业务日历 | 刚性节点齐备，有 T-30 倒排 | 核对日历台账 |
| 价值翻译 | 每指标有业务与财务影响，有出处 | 抽查翻译表 |
| 目标挂靠 | 项目逐项挂靠，挂不上 ≤ 10% | 核对挂靠清单 |
| 客户确认 | 客户认可翻译与地图 | 核对确认记录 |

关键项是业务地图、价值翻译和目标挂靠。任一关键项未通过，业务洞察实战不得视为合格。

## 8.6 执行故障排查

| 症状 | 常见原因 | 处理动作 |
| --- | --- | --- |
| 地图客户不认 | 闭门造车 | 拉客户共创一轮 |
| 日历总错过节点 | 倒排没做 | 补 T-30 动作并挂提醒 |
| 客户退回价值翻译 | 财务影响没出处 | 补底稿再送 |
| 客户嫌报告太技术 | 翻译没到位 | 按公式重翻一遍 |
| 客户质疑挂靠 | 挂得牵强 | 回到部门目标重挂 |
| 节点定性反复 | 判定无留痕 | 日历里补判定理由 |
| 翻译被整体打折 | 踩了翻译禁区 | 按三禁区逐条自查 |
| 高层复述不出价值 | 叙事没进高层语言 | 用一页纸重写（[第 10 章](ch10-relationship-management-practical.md)） |

反复出现的问题进入复盘流程（[附录 R](appx-r-problem-retrospective-standard.md)）。

## 8.7 执行检查清单

- [ ] 我能画出所负责客户所处行业的业务主线图
- [ ] 我手头的业务日历是最新的，且每个节点有倒排动作
- [ ] 我读过负责客户最近一年的年报战略章节
- [ ] 手头每个项目都能一句话说清挂到哪条业务目标
- [ ] 最近一次服务报告里，每个指标都带了业务影响
- [ ] 我与客户业务侧至少每季度有一次直接对话
- [ ] 我做的量化价值表达都注明了数据出处或假设
- [ ] 客户 CIO 层面有人能复述我团队带来的业务价值

---

**本章要点回顾**

1. 业务地图四步：选行业、画主线、标依赖、标峰值。客户确认才算数。
2. 业务日历三类节点都要记。刚性节点必倒排 T-30 动作。
3. 价值翻译走三段公式：技术指标 → 业务影响 → 财务影响。量化必须有出处。
4. 目标挂靠逐项验证。挂不上的工作要警惕。
5. 验收五项，关键项是地图、翻译和挂靠。
