# 第 23 章　金融级可用性架构护航

> 金融级可用性不是一张高可用架构图。它是架构、演练和纪律的组合。架构提供切换能力。演练验证能力真实存在。纪律保证变更和回退不失控。本章解决五类操作。评审架构。组织演练。管理冻结窗口。守住灰度与回退。管理峰值容量。本章为 How-to。可用性数学与容量方法见[第 5 章](ch05-technical-depth.md)，监管背景见[第 22 章](ch22-financial-industry.md)。

## 23.1 前置条件与目标

金融核心系统的可用性主张，必须按峰值场景验收。年平均值不能作为唯一依据。99.95% 的月度预算约 21 分钟。若中断落在年终决算深夜，业务后果可能远超普通时段。

开始前先确认以下输入。缺项时先补齐，或登记为风险。

| 前置条件 | 检查内容 | 缺项处理 |
| --- | --- | --- |
| 可用性目标 | 服务等级协议（SLA）、业务峰值要求与监管口径 | 与客户科技和业务确认 |
| 恢复目标 | 恢复点目标（Recovery Point Objective，RPO）与恢复时间目标（Recovery Time Objective，RTO） | 区分设计值与实测值 |
| 架构基线 | 两地三中心、双活、主备或单元化形态 | 用[模板 03](tpl-03-architecture-review-checklist.md)核对 |
| 切换手册 | 切换步骤、依赖、验证与回退 | 先补手册，再安排演练 |
| 依赖清单 | DNS、配置中心、审批、网络与关键人 | 纳入架构评审 |
| 数据一致性方案 | 复制方式、核对、追平与回切 | 由架构与数据团队确认 |
| 容量基线 | 峰值模型、水位与备端容量 | 按[第 5 章](ch05-technical-depth.md)补建 |
| 冻结日历 | 决算、结息、检查、重保与峰值 | 纳入[服务计划](tpl-01-service-plan.md) |
| 角色与授权 | 演练指挥、切换审批、回退授权 | 书面确认 |

完成标志有五项。架构风险有评审结论。切换能力有实测证据。冻结窗口有同步留痕。回退有预授权与演练。峰值容量有模型和复盘。

| 目标 | 完成标志 | 主要证据 |
| --- | --- | --- |
| 架构真实 | 设计口径与实测差距可解释 | 评审记录与演练数据 |
| 切换可用 | 业务验证通过，时间达成目标 | 演练时间线 |
| 冻结可控 | 相关方知道窗口和例外规则 | 同步记录 |
| 回退可信 | 回退方案实测或演练过 | 回退记录 |
| 峰值可承载 | 扩容、压测和降级完成 | 容量模型与压测报告 |

## 23.2 操作一：评审可用性架构

### 23.2.1 常见形态

| 形态 | 能力 | 代价与风险 |
| --- | --- | --- |
| 两地三中心 | 同城双中心抗机房故障，异地中心抗城市级灾难 | 成本高，切换与数据一致性复杂 |
| 双活 | 多中心同时承载流量，互为冗余 | 数据一致性、路由和冲突处理复杂 |
| 主备 | 备中心待命，故障时拉起 | 切换存在真空期，备端容量容易不足 |
| 单元化 | 流量按维度分片，单元全栈闭环 | 路由层可能成为新单点，跨单元事务复杂 |

形态没有天然优劣。评审要看业务峰值、故障代价、恢复目标和管理能力。

### 23.2.2 五个评审点

| 评审点 | 必须核实 | 常见纸面风险 |
| --- | --- | --- |
| RPO／RTO | 最近一次演练实测值 | 报的是设计理论值 |
| 切换依赖链 | DNS、配置中心、审批、网络、关键人 | 灾难时依赖项先失效 |
| 数据一致性 | 异步复制、核对、追平、对账 | 只练切换，不练数据修复 |
| 回切方案 | 回切条件、步骤和验证 | 只切过去，不切回来 |
| 备端容量 | 备中心或备单元承载全量的能力 | 长期半配，切换后过载 |

### 23.2.3 操作步骤

1. 读取架构基线、可用性目标与最近演练记录。
2. 区分设计值、合同值和实测值。三者不一致时记录差距。
3. 沿切换步骤核对依赖项。确认每项在灾难场景下的可用性。
4. 核对数据复制方式、核对流程与回切流程。
5. 核对备端容量是否承载峰值全量。
6. 对单元化架构，检查路由层和跨单元事务。
7. 将缺口写入风险登记册，指定 Owner 与期限。
8. 输出评审结论、遗留条件与复核时点。

评审使用[模板 03](tpl-03-architecture-review-checklist.md)。风险登记规则见[第 14 章](ch14-risk-compliance-practical.md)。

## 23.3 操作二：组织容灾演练

### 23.3.1 演练分级

| 级别 | 形态 | 建议频次 | 验证重点 |
| --- | --- | --- | --- |
| 桌面推演 | 按剧本走流程，不触生产 | 季度 | 角色、步骤与决策点 |
| 模拟演练 | 隔离环境执行切换 | 半年 | 技术动作与时间 |
| 实战切换 | 生产流量真实切换 | 按客户监管与制度确认 | 端到端业务能力 |

频次以客户制度、监管口径和合同为准。金融核心客户通常至少保留年度实战或等效演练。具体安排见[附录 K](appx-k-incident-emergency-drill-standard.md)。专有云责任边界见[附录 Q](appx-q-tam-service-quality-standard-dedicated-cloud.md)。

### 23.3.2 演练前步骤

1. 确认演练目标。验证切换、回切、数据核对或降级预案。
2. 选择场景。优先覆盖高风险依赖链。
3. 将窗口纳入业务日历，避开冻结与峰值节点。
4. 获得客户授权。确认生产操作的审批和回退权限。
5. 评审剧本。包含故障注入、观察点、回退触发线与业务验证脚本。
6. 确认厂商侧资源。专家待命、回退支持和升级路径写入方案。
7. 指定记录员。时间线从演练第 0 分钟开始。

### 23.3.3 演练中要求

1. 按作战室机制运行。角色参见[第 18 章](ch18-escalation-crisis.md)。
2. 只允许一个指挥官。回退触发按预授权执行。
3. 技术切换后必须执行业务验证。柜面、手机银行、批处理或关键交易按场景选择。
4. 记录每个关键时点。发现时间、决策时间、切换开始、业务恢复、数据核对完成。
5. 中途触发回退时，不视为失败。完整记录触发原因和耗时。

### 23.3.4 演练后步骤

1. 对比 RPO／RTO 口径值与实测值。
2. 汇总卡点、依赖失效、决策延迟和数据差异。
3. 修订切换手册、回退手册和业务验证脚本。
4. 将问题写入风险登记册，指定 Owner 与期限。
5. 复查上次演练遗留项是否闭环。

演练发现问题叫成功。年年“圆满成功”反而应怀疑场景不够真实。演练的主要产出是修订后的手册，不是通过结论。

## 23.4 操作三：管理变更冻结窗口

### 23.4.1 冻结日历

冻结窗口来自业务与监管日历。常见窗口包括年终决算、季末结息和重大活动重保。监管检查期也常需要冻结。部分机构还会纳入月底批处理窗口。

| 窗口类型 | 风险来源 | 管理要求 |
| --- | --- | --- |
| 年终决算 | 账务正确性与监管报送 | 通常全面冻结，只保留紧急通道 |
| 季末结息 | 批处理与数据一致性 | 禁止影响账务链路的变更 |
| 监管检查 | 证据链与整改事项 | 避免无关变更污染证据 |
| 重保期 | 业务峰值与舆情风险 | 只放行完成预审的关键变更 |
| 月底批处理 | 批处理窗口与资源争抢 | 按客户制度收窄窗口 |

### 23.4.2 操作步骤

1. 从客户科技、业务和合规口径收集冻结日历。
2. 将日历写入服务计划，并标注适用系统。
3. 同步厂商侧、平台侧、驻场和客户接口人。
4. 在变更评审中核对窗口。冲突申请直接顺延。
5. 窗口前一周完成三方提醒，并保留记录。
6. 冻结期内只处理符合例外条件的变更。
7. 解冻后复盘窗口内变更量和例外率。

### 23.4.3 例外机制

冻结期例外必须同时满足四项。理由属于生产事故修复或监管要求。客户变更委员会特批。双人复核执行。事后复盘回答为什么没有提前安排。

例外是窄门，不是日常通道。月度例外率持续偏高，说明计划能力或窗口设计有问题。

### 23.4.4 冻结前抢跑潮

大量变更挤在冻结前最后窗口，会稀释准备度。这种安排也会推高事故概率。处置方式如下。

1. 冻结前一周设变更预审峰会。
2. 只放行范围、窗口和回退都扎实的变更。
3. 其余变更明确顺延到解冻后。
4. 对高风险变更安排单独观察期。

变更纪律与记录单见[附录 T](appx-t-online-change-standard.md)和[模板 18](tpl-18-change-request-record.md)。

## 23.5 操作四：守住灰度与回退

### 23.5.1 灰度四问

金融核心链路每次发布都应回答四问。

| 问题 | 必须明确 | 常见缺陷 |
| --- | --- | --- |
| 灰度粒度 | 按机构、用户、流量或区域切分 | 第一批对象随机选择 |
| 观察指标 | 错误率、延迟、业务成功率和资源水位 | 只看技术指标，不看业务结果 |
| 拍板人 | 扩量、暂停和回退的决策人与时限 | 现场反复“再观察十分钟” |
| 回退路径 | 触发线、步骤、数据兼容与验证 | 只写重新部署旧版本 |

### 23.5.2 回退三条金融级加码

1. **数据兼容性前置验证**。新版本写入新格式后，旧版本必须能读取。无法直接读取时，必须完成转换。回退后数据怎么办，要在评审时说清。
2. **回退决策预授权**：事先约定指标越线即回退，无需临时开会。故障时的临时决策链通常慢于预设触发线。
3. **回退也要演练**：每年至少安排一次真实回退演练。它可结合容灾演练执行。没练过的回退方案按不存在处理。

### 23.5.3 操作步骤

1. 发布前填写灰度四问。
2. 将观察指标阈值写入发布方案。
3. 为每个阈值绑定动作：继续、暂停、扩量或回退。
4. 确认拍板人和替补，写明响应时限。
5. 灰度期间按固定节拍发布状态。
6. 触发回退时执行预授权，不再临时争论。
7. 回退后核对数据一致性和业务验证。
8. 发布结束复盘灰度效果和阈值准确性。

## 23.6 操作五：管理峰值容量

### 23.6.1 峰值容量原则

金融可用性的验收场景是峰值，不是平均值。决算日、结息日、大促和行情极端日，都要单独建模。

### 23.6.2 操作步骤

1. 收集历史峰值、业务增长计划和新增场景。
2. 为每个峰值日建立容量模型。
3. 按核心资源设置水位线。核心资源水位达到 80%，触发扩容评审。
4. 峰值前 30 天完成扩容和压测。
5. 压测目标不低于预测峰值的 1.5 倍。安全系数按客户风险偏好校准。
6. 评审降级开关、限流阈值和非核心功能降级顺序。
7. 演练降级预案，确认业务可感知影响。
8. 峰值后比较实际值与预测值，回写容量模型。

容量方法见[第 5 章](ch05-technical-depth.md)。质量口径见[第 34 章](ch34-measurement-system.md)与[附录 Q](appx-q-tam-service-quality-standard-dedicated-cloud.md)。

## 23.7 验收标准

| 验收项 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 架构评审 | 五个评审点有结论和遗留项 | 抽查评审记录 |
| 恢复目标 | 口径值与实测值差异可解释 | 核对演练时间线 |
| 切换能力 | 最近演练包含业务验证 | 核对演练报告 |
| 回切能力 | 回切步骤、数据核对和验证成文 | 抽查手册与记录 |
| 冻结管理 | 日历入服务计划，三方提醒留痕 | 核对服务计划与记录 |
| 例外控制 | 特批、双复核和复盘齐备 | 抽查例外变更 |
| 灰度回退 | 四问答齐，回退触发线预授权 | 抽查发布方案 |
| 峰值容量 | 模型、压测、降级演练和复盘齐备 | 核对容量档案 |

关键项包括实测切换、回切能力和冻结例外控制。未通过前不得视为金融级可用性护航合格。

## 23.8 执行故障排查

| 症状 | 常见原因 | 处理动作 |
| --- | --- | --- |
| 纸面 RTO 很好，演练很差 | 目标未实测或场景过窄 | 重新设计场景，记录真实耗时 |
| 切换后业务不可用 | 依赖链未纳入切换演练 | 补依赖清单并重演 |
| 切换成功但数据不一致 | 只练切换，不练核对与追平 | 增加数据一致性演练 |
| 回切长期不演练 | 怕二次风险或无人授权 | 单独立项，先桌面后实战 |
| 备端切换后过载 | 备端容量长期半配 | 纳入容量模型并扩容 |
| 冻结期频繁例外 | 计划不足或窗口太粗 | 复盘例外原因，调整预审 |
| 灰度无人拍板 | 决策人和时限缺失 | 补拍板矩阵和预授权 |
| 峰值预测连续偏差 | 模型缺业务日历或新场景 | 修正模型并复盘偏差来源 |

反复出现的可用性问题进入复盘流程。

## 23.9 常见误区

1. **把架构图当能力**：没有演练的容灾只是设计意图。
2. **用平均值验收**：年平均达标不能证明决算夜可用。
3. **只练切换不练回切**：回切失败会把事故变成二次事故。
4. **把冻结当阻碍**：冻结窗口是风险控制机制，不是行政障碍。
5. **把压测当形式**：目标不来自峰值模型。这种压测结果无法支持上线判断。
6. **让降级预案停留在文档里**。未演练的降级会带来未知业务影响。

## 23.10 执行检查清单

- [ ] 容灾形态、SLA、RPO 与 RTO 口径清晰
- [ ] 最近一次演练的 RPO／RTO 实测值可查
- [ ] 切换依赖链、回切方案和数据核对流程成文
- [ ] 备端容量可承载峰值全量
- [ ] 冻结日历入服务计划，三方提醒有留痕
- [ ] 冻结期例外有特批、双复核和复盘
- [ ] 核心发布完成灰度四问
- [ ] 回退触发线已预授权，回退方案演练过
- [ ] 峰值容量模型、压测和降级演练已完成或排期
- [ ] 峰值后复盘已回写容量模型

---

**本章要点回顾**

1. 金融级可用性是架构、演练和纪律的组合。多数事故输在纪律，不输在单点技术。
2. 可用性主张按峰值场景验收。年平均值不能证明决算夜可用。
3. 架构评审核实五个点。它们是恢复目标、切换依赖、数据一致性、回切和备端容量。
4. 演练分桌面、模拟和实战。主要产出是修订后的手册，不是通过结论。
5. 冻结日历入服务计划，三方同步留痕。例外是窄门，不能成为日常通道。
6. 灰度四问加回退三条加码。发布因此可观察、可决策、可回退。
7. 峰值容量按日历建模。水位、压测、降级和复盘共同构成峰值护航。
