# AGENTS.md — The TAM Book of AI Era

本文件是本仓库对 AI 编程/写作 Agent 的约定，进入本仓库的 Agent 须先读完本文件与 `HANDOFF.md` 再开始工作。

> **自动加载 Skill**：本仓库涉及写作/编辑任务时，Agent 须自动加载 `.qoder/skills/allen-writes/SKILL.md` 作为写作规范。

## 项目简介

开源技术图书《The TAM Book of AI Era｜AI 时代的 TAM 白皮书》。以 TAM（Technical Account Manager）岗位最佳实践为根本，以 AI 时代的变化为主线课题，目标是让读者能在企业级、金融级顶级大项目中落地。

- 目录唯一事实源：`manuscript/00-outline.md`（改目录先改它，章节文件与其保持一致）
- 章节稿件：`manuscript/` 目录，一章一个文件
- 可复用模板/清单：`templates/` 目录（对应第七部分开源工具箱）
- 厂商官方原文归档：`well-architected/` 目录（**脚本生成的只读副本，勿手改正文**；要改解析规则或补抓，改 `well-architected/fetch_well_architected.py` 后重跑，说明见附录 Z.9.2）

## 通用规则

1. 用第一性原理思考：先确认真实目标、约束和成功标准，不要套用惯例。
2. 简单问题直接回复；复杂内容落成仓库里的文件，不要只在对话里长篇输出。
3. 踩过的坑、做过的关键决策写进 `HANDOFF.md`；执行新任务前先读 `HANDOFF.md`，避免重复踩坑。
4. 涉及上线、部署、生产环境的任务，把性能开销纳入设计和验收标准。
5. 涉及 UI：避免不必要的次级标签和说明文字，让布局自己解释。

## 写作约定

- 正文用中文，标点用全角；技术术语、产品名保留英文原词。
- 每章结构遵循目录文件中的设定（如内涵篇统一"定义 → 分级标准 → 训练方法 → 自检清单"）。
- 涉及具体公司/客户的案例一律脱敏虚构化，不使用真实客户名。
- 数据、行情、监管条文等时效性内容必须标注来源与时点，不凭记忆写死。
- 术语与目录文件保持一致，改动术语时同步更新附录 A。
- P 前缀编号四义并存（流程 P1–P12／故障级 P1–P4／评估原则 P1–P5／附录 P 节号 P.x），已裁定不改名（2026-10-25，Allen）：引用时首现带语境限定词（如"故障 P1""流程 P5"），歧义消解权威表为附录 A.8。
- 模板引用统一为"模板 01"格式（两位数字补零），禁止写成"模板01""模板 1"等变体。
- **配图约定（2026-11-17）**：图存 `manuscript/figures/*.svg`，正文用相对路径 `![替代文本](figures/xxx.svg)` 引用，替代文本必须说清图在讲什么（禁"见下图"式空 alt）。SVG 手写，中文字体栈 `-apple-system, 'PingFang SC', 'Microsoft YaHei', sans-serif`，viewBox 固定、不写死 width/height。图只承担"看懂结构"，不替代事实源表——数值口径仍以第 34 章与附录条文为准。新增图后跑 `python3 xref_check.py`（含图片路径存在性检查）。
- **数字必须带口径标注**。百分比、倍数、金额、时限四类硬断言，须从五类标注中选一：〔标准〕〔监管〕〔厂商〕〔经验值〕〔建议值〕。案例演示数字标〔案例虚构值〕。四类之外只剩三种合法形态：算术可复算的换算、本章案例虚构演示值、本书内部指向（第 X 章 / 附录 X / 模板 NN）。无口径的硬断言由 `scripts/claim_audit.py` 拦下。
- **自订标准件不得自称官方标准**。标题以"（拟定稿）"收尾，H1 下第一行写状态徽标四句（无机构背书、无外部评审、无企业试点、条文可引用可反驳）。引用时须连"（拟定稿）"一起写。门禁由 `content_gate.py` 的 `draft_badge_issues()` 执行。

## Diátaxis 文档类型约定

全书章节按 Diátaxis 框架划分为四种文档类型，每章须在文件头注释中标注所属类型。禁止同一章内混合两种以上类型；若内容需要，拆分为独立章节或迁移至附录。

| 类型 | 核心目的 | 典型结构 | 本书适用章节 |
|------|----------|----------|--------------|
| **Tutorial（教程）** | 引导读者通过实操获得可见成果 | 环境准备 → 分步骤操作 → 验证成果 → 常见错误 | 附录 J（培训教程）、附录 Y（训练教程） |
| **How-to Guide（操作指南）** | 解决特定真实世界问题的步骤 | 目标声明 → 前置条件 → 操作步骤 → 验收标准 | ch11（服务治理）、ch16（项目与变革）、ch18（升级）、ch24（重保） |
| **Reference（参考）** | 对机制、概念、数据的权威描述 | 定义 → 分类/列表 → 属性/参数 → 交叉引用 | appx-a（术语表）、appx-b（流程速查）、appx-g（评估标准）、ch02（边界对照表） |
| **Explanation（解释）** | 阐明背景、设计选择与权衡 | 问题背景 → 核心概念 → 因果关系 → 常见误区 | ch01（起源演进）、ch03（价值主张）、ch04（AI时代）、ch07（业务洞察）、ch09（关系管理） |

**类型标注格式**（每章文件首行注释）：
```markdown
<!-- Diátaxis: Explanation -->
# 第 1 章　TAM 的起源与演进
```

**自检清单分类**：
- Explanation 章使用"学习效果清单"——验证读者是否理解了"为什么"（如"能用自己的话解释三次跃迁的驱动力"）。
- How-to 章使用"执行检查清单"——验证读者是否完成了操作（如"服务计划已与客户共同签署"）。

## 内容门禁（交付前必跑）

形式质量（长句、被动、链接、表格列数）已经全部脚本化并通过。但这套门禁管不到内容厚度：全部通过之后，稿子仍可能通篇断言、无一数字。

`scripts/content_gate.py` 补这一层。它按 Diátaxis 类型分档，测论证密度、具象密度、清单化率、失效边界词、回顾占比与同构重复。

| 级别 | 含义 | 处置 |
|---|---|---|
| block | 体裁矛盾、结构破损 | 当期必修，`--strict` 拦发布 |
| warn | 内容厚度不足 | 进 `content-gate-report.md` 台账，不阻断发布 |

三条纪律（完整版与指标盲区见 `QUALITY-GATE.md`）：

1. **禁止为过线编造数据。** 没有量化对象就留 warn，并在章内注明原因。
2. **禁止为过线改变排版形态。** 形态服务内容，不服务指标。
3. **调阈值必须重跑 `--calibrate` 并记入 HANDOFF。**

新增附录前先过"附录准入三问"：能否并入现有附录？删掉哪条结论会站不住？同构审计落在哪个簇？自 2026-11-10 起不再接受同构落地件。

**体裁合并裁定（2026-11-17）**：标准件合并"执行落地"节后仍标 Reference（Tutorial 件标 Tutorial），执行内容以步骤/责任/验收表格承载，勾选项仅留验收清单；一章一体裁的约束针对整文件的 Diátaxis 标注，不禁止 Reference 条文内含执行性表格。

交付前六条命令：

```bash
python3 scripts/content_gate.py --strict
python3 scripts/content_gate.py --report
python3 scripts/claim_audit.py
python3 scripts/similarity_audit.py --report
python3 scripts/gen_metadata.py --check
python3 xref_check.py && python3 xref_check2.py
```

## 元数据（禁止手写数字）

文件数、类型分布、字数、模板数、标准库份数，一律不得手写。全部由 `scripts/gen_metadata.py` 从磁盘算。

文档里的数字用标记区包住：

```markdown
<!-- META:templates_count -->23<!-- /META:templates_count -->
```

改文件后跑 `python3 scripts/gen_metadata.py --write` 回填。`--check` 发现漂移退出码 1，拦发布。

四条规则：

1. **能算的不写。** 凡是脚本从磁盘能得到的数字，不进正文手写。
2. **标记区不手改。** `<!-- META:... -->` 之间的内容由脚本拥有。
3. **新增文件后重跑三件。** `--write` 回填数字，`--index` 重建索引，`--check` 确认无漂移。
4. **索引不进手改。** `manuscript/99-index.md` 是生成物，改章节标题或增删文件后重跑 `--index`。

新增前置页或导航件（`00-`、`99-` 开头）不计入 Diátaxis 分型统计，但要在 `manuscript/00-outline.md` 的前置页一节登记。

## AI 辅助写作技能（Agent Skills）

本仓库在写作流程中可调用以下 AI Agent Skills 提升效率与质量。进入对应任务时，Agent 须加载对应 Skill。

### 1. `/technical-writing` — Diátaxis 技术写作

**核心能力**：按 Diátaxis 框架（Tutorial / How-to / Reference / Explanation）将杂乱初稿重构为结构化技术文档。

**使用场景**：
- 新章节草稿完成后的类型对齐与结构调整
- 混合类型章节（如"定义+步骤+标准"混写）的拆分建议
- 自检清单生成（学习效果清单 vs 执行检查清单）

**关键原则**：
- Tutorial 必须是线性的、手把手的、以学习者为中心的
- How-to 必须解决特定真实世界问题，不解释背景
- Reference 必须是完整的、权威的、描述"是什么"
- Explanation 必须回答"为什么"，不给出操作步骤

### 2. `/writing-for-agents` — 面向 Agent 的文档写作

**核心能力**：优化 Agent 会读取的文档（AGENTS.md、SKILL.md、Prompt 等），提升 Agent 行为的可预测性。

**关键原则**（来自 Matt Pocock）：
- **默认动作是删除，不是解释** —— Agent 已知道的事情不要重复
- **每条指令都应该是"预测性行为改变"** —— 只写改变 Agent 行为的指令
- 关注 Context load（常驻上下文成本）和 Turn load（单次触发成本）的平衡

**使用场景**：
- 优化本仓库 AGENTS.md 的指令精度
- 编写新的 Agent Skill 文件
- 审查 Prompt 中是否存在"无意义上下文填充"

### 3. `/write-skills` — Skill 编写与优化

**核心能力**：指导如何编写高质量的 Agent Skill 文件。

**关键原则**（来自 dzhng/skills）：
- **Trigger from the description** —— 触发规则写在 description 里，不要藏在正文
- **Spend tokens like they are scarce** —— 只写改变 Agent 行为的指令
- A wrapper skill 可以只有两句话：命名能力 + 遵循的 skill

**使用场景**：
- 为本书创建自定义写作 Agent Skill
- 优化现有 Skill 的触发描述
- 判断内容应放入 Skill 还是普通文档

### 4. `/agent-style` — AI 技术写作风格 21 条

**核心能力**：让 AI 产出符合技术专家水准的文档，避免 AI 常见文风问题。

**覆盖范围**（来自 yzhao062/agent-style）：
- RULE-01：Curse of Knowledge（避免知识诅咒，不写"显然"）
- RULE-H：Citation discipline（引用纪律，来源可追溯）
- 避免 AI 常见套路：空泛开头、过度礼貌、被动语态、长句堆砌
- 适用于 API docs、design docs、READMEs、postmortems

**使用场景**：
- 初稿完成后统一润色，去除"AI 腔"
- 技术文档风格审查
- 与 `/unslop` 联合使用，双重净化

### 5. `/bmad-agent-tech-writer` — Paige 技术写作专家

**核心能力**：将复杂概念转化为结构化文档，支持多格式输出。

**支持格式**：CommonMark、DITA、OpenAPI、Mermaid
**特点**：
- 自定义角色配置（适配不同受众深度）
- 持久事实加载（保持术语和上下文一致性）
- 多语言输出能力

**使用场景**：
- 生成复杂章节（如架构评审、容量规划）的初稿
- 将口语化访谈内容转为结构化文档
- 跨章节术语一致性检查

### 6. `/report-writing` — 研究报告写作

**核心能力**：将研究笔记转化为正式交付物。

**适用场景**：
- 行业调研报告（如 ch01 五家体系对比的更新）
- 技术白皮书片段
- 多源研究成果整合为统一叙事

**关键输入**：
- 研究笔记（原始素材）
- 目标受众（技术/管理/业务）
- 交付格式（章节/附录/独立报告）

### 7. `/unslop` — 去除 AI 文风

**核心能力**：清除 AI 常见的"矫揉造作的散文"、"空洞的总结性开头"。

**典型修复**：
- "In today's rapidly evolving world..." → 直接切入主题
- "It's important to note that..." → 删除，直接说重点
- 被动语态 → 主动语态
- 长句 → 短句（技术越复杂，语言越简单）

**使用场景**：
- 每章初稿完成后必做的一道"去 AI 化"工序
- 与 `/agent-style` 联合使用

### 8. 软件文档自动化 Skills（10 件套）

**核心能力**：在文档生命周期各阶段自动产出或维护技术文档。

| Skill | 作用 | 本书应用场景 |
|-------|------|-------------|
| **README 生成** | 从项目结构反推项目说明 | 本仓库 README 维护 |
| **API 文档自动提取** | 解析函数签名生成接口文档 | 若后续开源配套工具 |
| **Docstring 规范化** | 检查并补全文档字符串 | 配套脚本文档化 |
| **Changelog 自动生成** | 从 commit 历史生成变更日志 | 版本发布时 |
| **Code Review 摘要** | 将 PR 差异总结为技术说明 | 重大修改的章节说明 |
| **Onboarding 指南** | 为新成员生成项目上手文档 | 新贡献者引导 |

### 9. `/skill-creator` — 元技能

**核心能力**：指导创建新的 Agent Skill，通过四阶段工作流确保质量。

**四阶段**：
1. **发现**：识别重复性工作流
2. **需求分析**：明确技能边界和触发条件
3. **规范设计**：定义输入、输出、行为约束
4. **生成验证**：测试技能的可复用性

**使用场景**：
- 为本书创建自定义写作 Skill（如"/tam-style"）
- 评估现有 Skill 是否需要合并或拆分

### 10. `/grill-with-docs` — 文档审查与一致性维护

**核心能力**：审查和审计技术文档，确保多语言/多章节的一致性和质量。

**功能**：
- 检查文档与代码（或事实源）的一致性
- 多章节术语同步审计
- 识别过时或矛盾的描述
- 贡献指南和多语言文档维护

**使用场景**：
- 全书完稿前的统一审查
- 术语表（appx-a）与正文引用的交叉验证
- 新增章节与已有章节的概念一致性检查
