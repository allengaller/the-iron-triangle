# 第 14 章　风险与合规实战

> 本章解决两个执行问题。第一，如何在事故发生前看见并处理风险。第二，如何在监管与审计到来前备好证据。目标产物是四样。一份持续运行的风险登记册。三条固定节奏的扫描线。一套审计配合机制。一组数据安全边界控制。本章为 How-to。概念背景见[第 11 章](ch11-service-governance.md)，训练方法见[附录 Y](appx-y-training-tutorial.md)。

## 14.1 前置条件与目标

开始前先确认前置条件。缺少条件时，先完成对应准备，再进入后续操作。

| 前置条件 | 完成标志 | 缺项处理 |
| --- | --- | --- |
| 客户授权 | 明确风险沟通与数据使用范围 | 与服务负责人确认授权 |
| 登记册载体 | 使用[模板 09](../templates/09-risk-register.md)或等价系统 | 先建最小台账，再补字段 |
| 业务日历 | 关键节点与冻结窗口可得 | 从第 7 章方法补建 |
| 资产与版本清单 | 系统、组件与版本状态可查 | 从第 11 章台账补全 |
| 数据分级口径 | 客户数据分类与使用边界明确 | 向客户安全接口确认 |
| 证据留存机制 | 值班、变更与事件记录可持续获取 | 先修记录链，再谈配合 |

### 14.1.1 目标与完成标志

执行目标是让风险可见、责任可追、证据可用、边界可守。完成标志不是文档齐全。机制要在下一次事件或审计中经得起抽查。

| 目标 | 完成标志 | 主要产物 |
| --- | --- | --- |
| 风险可见 | 新风险能进入登记册并分级 | 风险登记册 |
| 责任可追 | 每条风险有 Owner 与复审日期 | 台账记录 |
| 证据可用 | 抽查事件可还原完整链 | 证据索引 |
| 边界可守 | 数据与 AI 使用有授权记录 | 使用与授权记录 |

### 14.1.2 风险与合规必须分开管理

| 对照项 | 风险 | 合规 |
| --- | --- | --- |
| 问题性质 | 概率与影响 | 规则与底线 |
| 可选动作 | 接受、缓解、转移、规避 | 遵守，或承担明确代价 |
| 判断方式 | 权衡取舍 | 判断是否违反 |
| 典型证据 | 概率评估与缓解记录 | 制度依据与执行证据 |
| 常见错误 | 当成禁令，工作停滞 | 当成概率，先上线再说 |

风险管理允许接受残余风险。合规管理不存在“接受违规”的常规选项。两类条目可以在同一本册中管理，处置逻辑必须分开。

### 14.1.3 TAM 的角色边界

TAM 是现场风险传感器与合规第一公里。角色包含三项动作。识别信号，按规定上报，提供可核验证据。

TAM 不是风险部门，也不是合规官。TAM 不替代客户风险决策，不替代法务结论，也不自行认定违规。发现边界问题时，TAM 的责任是尽快让有权角色知晓。

## 14.2 操作一：建立并运行风险登记册

风险登记册是风险的唯一事实源。以下步骤用于建立与月度运行。

1. **收集来源**：汇集架构评审结论与 SLA 偏差。健康检查、重保体检也纳入。组织异动与一线反馈同样进入收集范围。
2. **写清描述**：采用三要素写法。条件、坏事与影响对象都要写清。
3. **分类定级**：标注技术、业务、组织或合规类别。概率与影响各分三档。
4. **指定 Owner**：每条风险指定具名负责人。客户侧风险应确认客户 Owner。
5. **定义动作**：写明缓解动作、期限与验证方式。没有动作的条目不入册。
6. **设定复审**：给出复审日期。高风险条目缩短复审周期。
7. **重大风险会签**：高概率或高影响条目与客户书面确认。记录接受、缓解或升级结论。
8. **月度过册**：在月度服务回顾中逐条过册。同步更新状态与等级。
9. **关闭验证**：动作完成后验证效果。确认残余风险与后续观察期。

### 14.2.1 登记字段规则

| 字段 | 合格写法 | 不合格写法 |
| --- | --- | --- |
| 描述 | 双活切换依赖人工确认，故障时可能超时 | 系统存在可用性风险 |
| Owner | 客户运维主管张某，厂商侧李某 | 双方共同关注 |
| 动作 | 完成自动化切换脚本并演练一次 | 加强关注 |
| 期限 | 具体日期 | 尽快 |
| 复审 | 具体日期 | 待定 |

Owner、动作与复审日期缺一不入册。缺少任一项时，条目只能作为线索留在扫描记录中。

### 14.2.2 关闭验证不能看动作是否完成

动作完成不等于风险消除。关闭前需要确认结果。验证方式包括指标复查、演练结果、变更记录与客户确认。

无法立即验证的风险可以转入观察期。观察期仍需 Owner 与复审日期。长期无法关闭的风险应升级或重新评估等级。

已接受的风险也要保留记录。接受不等于遗忘。复审日期到达时，仍需重新确认接受条件是否成立。

### 14.2.3 会签与升级

重大风险会签的目的是共同决策。会签记录应包含风险描述、影响、建议动作、接受结论与责任人。

需要升级的情形包括三类。风险超出客户接口授权范围。缓解动作长期无资源。合规边界出现疑似违反。

升级不改变风险归属。TAM 仍负责事实与证据，客户授权角色负责接受与决策。

### 14.2.4 登记册与其他台账的接口

登记册不是唯一台账。它与变更、资产、事件和承诺台账存在接口。接口不清时，同一问题会在多处重复登记。

| 相邻台账 | 输入登记册的内容 | 回写方向 |
| --- | --- | --- |
| 变更台账 | 变更引入的新风险 | 风险缓解动作转为变更条件 |
| 资产台账 | 版本与配置差异 | 关闭结果更新基线 |
| 事件与复盘 | 暴露的未决风险 | 改进项进入风险动作 |
| 承诺台账 | 承诺无法兑现的迹象 | 风险升级促发承诺变更 |

接口维护有两条规则。风险事实在登记册中保持主记录。专项台账引用编号，不复制结论。这样既保留源头，也避免多处状态冲突。

## 14.3 操作二：运行三道风险扫描线

登记册管理已知风险。扫描用于发现未知风险。三条扫描线需固定节奏，产出统一汇入登记册。

| 扫描线 | 主要输入 | 优先发现 | 常见盲区 |
| --- | --- | --- | --- |
| 技术线 | 水位、版本、依赖与配置 | 容量、单点与生命周期风险 | 隐性依赖与配置漂移 |
| 业务线 | 业务日历与服务安排 | 峰值、冻结与值守缺口 | 临时活动与口径变化 |
| 组织线 | 关键人、预算与团队状态 | 关系断层与资源收缩 | 决策链重组 |

### 14.3.1 技术扫描步骤

1. 读取容量水位与增长趋势。标记接近阈值的系统。
2. 对照版本台账。标记逼近生命周期终止的组件。通告来源见[附录 F](appx-f-cloud-vendor-notices-2026.md)。
3. 检查单点与隐性依赖。确认 DNS、证书与时间源等基础依赖。
4. 抽查配置基线并记录漂移项。
5. 将确认风险按登记册规则入册。

### 14.3.2 业务扫描步骤

1. 读取客户业务日历。列出未来一个季度的刚性节点与峰值窗口。
2. 对每个节点检查三项条件。容量余量、冻结纪律与值守排班都要确认。
3. 核对重保与演练安排。确认回退方案可用。
4. 将缺口写入登记册。标注业务窗口影响。

业务窗口是风险放大器。同一故障发生在决算日与普通工作日，等级不同。定级时需要把窗口因素写入。

### 14.3.3 组织扫描步骤

1. 对照关键人地图，识别关键人变动、缺席与覆盖空白；
2. 收集预算、决策链与组织调整信号；
3. 检查服务团队自身人员变化与交接状态；
4. 将关系断层、资源收缩与承诺失效迹象入册。

组织线最容易遗漏。系统指标全绿时，客户关系与决策链仍可能发生剧烈变化。人员变动后的承诺需要重新确认。

### 14.3.4 扫描节奏与产出规则

| 节奏 | 范围 | 典型产出 |
| --- | --- | --- |
| 每周快扫 | 自动化告警与重点信号 | 新增线索与等级变化 |
| 每月深扫 | 结合服务回顾系统检查 | 入册条目与行动更新 |
| 每季体检 | 结合 QBR 全面复查 | 台账清理与专项计划 |

扫描产出必须汇入登记册。长时间只扫描不入册，会让风险留在个人笔记中。重复线索应合并，避免同一风险多个编号。

### 14.3.5 AI 辅助扫描

AI 适合做信号聚合与异常初筛。它能外推趋势，也能从通告与变更文本中提取候选风险。它还能帮助发现历史模式。

风险定性仍由人负责。是否构成风险、属于哪级，需要结合客户语境判断。影响哪些业务也要由人确认。AI 输出属于候选信号，不直接成为登记条目。

使用 AI 前必须过数据边界。客户日志、拓扑与业务数据进入工具前，先确认授权与分级。具体边界见 14.5。

### 14.3.6 扫描信号的分流规则

扫描会产生大量线索。分流规则决定哪些进入登记册，哪些继续观察。规则统一后，团队判断才不会各行其是。

| 线索状态 | 处理方式 | 记录要求 |
| --- | --- | --- |
| 已确认风险 | 按登记规则入册并定级 | 完整字段与 Owner |
| 可能风险 | 进入观察清单，设定核查期限 | 线索来源与核查动作 |
| 重复线索 | 合并到既有条目 | 保留来源关联 |
| 已存在缓解 | 评估动作是否仍有效 | 更新复审日期 |
| 误报 | 记录排除依据 | 防止重复排查 |

分流不需要复杂评分表。关键是每条线索有去向。没有去向的线索会在下一次扫描中重新出现。

分流结果应支持复核。客户或团队抽查时，应能看出某条线索为何入册或排除。判断依据也是治理证据。

## 14.4 操作三：配合审计与监管检查

审计与监管检查是常态事件。TAM 的角色是证据提供者与口径把关人。响应过程需要操作顺序与授权边界。

### 14.4.1 事前建立证据索引

平时的记录决定事后的响应速度。TAM 应维护证据索引，列明材料位置、责任人与更新时间。

| 证据类型 | 典型材料 | 常见缺口 |
| --- | --- | --- |
| 服务履行 | 服务计划、例会纪要、月报 | 行动项未闭环 |
| 事件处置 | 值班日志、事件时间线、复盘 | 时间线版本不一致 |
| 变更管理 | 变更申请、审批与回执 | 紧急变更未补办 |
| 演练与重保 | 演练记录、值守排班 | 演练未实战验证 |
| 数据与合规 | 授权记录、分级清单、脱敏检查 | 授权范围过期 |

### 14.4.2 检查中的响应步骤

1. **确认接口**：明确客户与厂商两侧授权接口。对外材料由授权接口输出。
2. **确认范围**：核对检查事项、时限与材料清单。避免扩大收集范围。
3. **调取证据**：按索引收集原始记录。保留来源与时间信息。
4. **核验口径**：涉及指标与结论时先核对口径。与内部事实、合同口径保持一致。
5. **提交与留痕**：记录提交版本、时间与接收人。
6. **跟踪问题**：检查方提出的事项进入台账。明确 Owner 与整改期限。
7. **复盘改进**：检查结束后复盘缺口。更新证据索引与日常机制。

### 14.4.3 三项纪律

**如实**：不修饰、不隐瞒、不替客户美化材料。监管一旦发现材料注水，厂商信用会一次清零。

**留痕在平时**：证据链是日常治理的副产品。审计前突击补材料，补出的痕迹本身会成为问题。

**口径一致**：对外数字与结论必须与内部事实一致。输出只由授权接口完成。随口解释会制造第二套事实。

监管事件的上报口径与时限要求见[第 25 章](ch25-financial-incident.md)。金融行业特殊制度见[第 22 章](ch22-financial-industry.md)。

### 14.4.4 问询配合的角色边界

检查与问询现场经常出现临时追问。TAM 需要守住三个角色边界。

第一，**事实与定性分开**。事实可以按证据说明。责任定性交由授权角色与制度判断。

第二，**己方与客户分开**。涉及客户内部管理的问题，由客户接口回答。TAM 不替客户解释其决策动因。

第三，**已知与推测分开**。尚未查明的事项明确说明状态与下次更新时点。现场推测会成为后续记录。

边界不等于沉默。TAM 应主动提供技术事实与材料位置。越清楚的事实边界，越能减少误解。

## 14.5 操作四：守住数据安全边界

TAM 接触客户拓扑、配置、日志与业务数据。这些数据是信任的实物形态，也是风险载体。

### 14.5.1 三项前置判断

任何数据使用前先回答三个问题。数据属于什么级别。使用环境是否在授权范围。用途与期限是否匹配。

| 判断项 | 合格条件 | 常见错误 |
| --- | --- | --- |
| 数据级别 | 已按客户分级识别 | 默认“技术数据不敏感” |
| 使用环境 | 客户授权环境或合规通道 | 直接粘贴到公网工具 |
| 用途与期限 | 与授权一致且到期处理 | 授权过期仍继续使用 |

### 14.5.2 三条铁律

1. **数据不出授权边界**：客户数据的使用受授权约束。环境、期限与用途都必须在范围内。带离即违规，不论动机。
2. **进 AI 工具前先问能不能进**：输入前先数据分级。工单内容、日志片段与架构图都要过界。工具清单与分级需对照核查。
3. **脱敏是可验证动作**：材料对外前按清单检查。口头声明不算脱敏。

脱敏清单至少覆盖六类特征。客户名、域名、IP、账号、系统路径与业务数字。检查应留下记录与检查人。

### 14.5.3 疑似违规的处理顺序

1. 立即停止扩散，保留现状证据；
2. 按客户与公司要求上报，不自行判定性质；
3. 配合调查并提供事实；
4. 复盘原因并更新控制措施；
5. 验证改进有效后关闭。

隐瞒比违反本身严重。违反属于事故，隐瞒属于诚信事件。前者可通过整改修复，后者会击穿信任账户底层。

### 14.5.4 数据全生命周期控制

数据边界不只发生在输入时刻。采集、使用、共享、留存与销毁都需要控制。

| 阶段 | 控制动作 | 常见缺口 |
| --- | --- | --- |
| 采集 | 确认目的与最小范围 | 顺手多取，范围失控 |
| 使用 | 在授权环境与期限内操作 | 授权过期仍继续使用 |
| 共享 | 核对接收方与用途 | 转发超出原授权 |
| 留存 | 到期清理或延期审批 | 临时文件长期滞留 |
| 销毁 | 按客户要求处理副本 | 遗漏本地副本 |

个人设备与协作工具是常见遗漏点。下载记录、聊天转发与临时目录都可能留存数据副本。控制措施应覆盖这些位置。

## 14.6 验收标准

执行完成后，用以下标准验证机制是否真实运行。

| 验收项 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 登记册运行 | 本月过册，无三缺一条目 | 抽查 5 条记录 |
| 会签完整 | 重大风险有客户确认记录 | 核对会签文件 |
| 扫描产出 | 三线各有记录且汇入登记册 | 核对扫描与入册轨迹 |
| 证据链 | 抽取事件 30 分钟内给出完整链 | 现场演练 |
| 数据边界 | AI 工具与数据分级已对照 | 核对工具清单 |
| 脱敏有效 | 近期外发材料有检查记录 | 按清单抽查 |

任一验收项失败，先修复对应机制。不要用补文档方式通过验收。验收的目的是确认下一次事件或审计能够应对。

### 14.6.1 验收时机与记录

验收按三种时机执行。月度服务回顾中检查登记册与扫描。季度检查中复核证据索引与数据边界。重大事件或审计结束后做专项复核。

验收记录应包含抽查对象、发现问题和整改跟踪。发现问题不等于验收失败。发现问题长期不整改，才说明机制失效。

验收结果可进入服务质量记分。它与[附录 G](appx-g-tam-work-evaluation-standard.md)使用同一数据源，不重复填报。

## 14.7 执行故障排查

| 症状 | 常见原因 | 处理动作 |
| --- | --- | --- |
| 登记册变成考古现场 | 月度过册中断，复审流于形式 | 恢复月度议程，先清理过期条目 |
| 扫描没有产出 | 扫描无固定节奏或无人负责 | 固定节奏与负责人，产出必须入册 |
| 风险写了却不关闭 | 动作缺少期限与验证方式 | 补齐 Owner、期限与关闭验证 |
| 客户拒绝会签 | 风险描述或影响不清楚 | 改写描述，先与接口人沟通 |
| 审计前突击补材料 | 日常留痕机制缺失 | 重建证据索引，修复记录链 |
| AI 使用越界 | 工具与数据分级未对照 | 停用问题场景，补授权与替代通道 |
| 外部指出脱敏问题 | 检查清单缺失或未执行 | 补全清单，增加复核环节 |

排查原则是先修机制，再处理个案。反复出现的同类问题，应进入复盘流程，按[附录 R](appx-r-problem-retrospective-standard.md)处理。

## 14.8 常见误区

1. **登记册变免责簿**：把风险抄送客户，出事时说早已写过。登记册用于消灭风险，不是划责工具；
2. **合规是合规部门的事**：第一公里没人守。后面每一公里都在补救。
3. **只扫技术不扫组织**：系统稳定而组织变化。续约与服务承诺仍会受冲击。
4. **用风险逻辑处理违规**：把合规问题当成概率权衡。结果是底线让位进度。

## 14.9 执行检查清单

- [ ] 每个负责客户有风险登记册，本月完成过册
- [ ] 每条风险有具名 Owner、缓解动作与复审日期
- [ ] 重大风险全部完成双方会签
- [ ] 三道扫描线各有节奏，本月有新风险入册
- [ ] 业务日历高危窗口的冻结与值守安排已就绪
- [ ] 任意抽取近期事件，30 分钟内可给出完整证据链
- [ ] AI 工具清单与客户数据分级完成对照
- [ ] 近期外发材料按清单验证过脱敏并留有记录

---

**本章要点回顾**

1. 风险是概率题，合规是判断题。两类条目可以同册管理，处置逻辑必须分开。
2. 登记册是风险唯一事实源。Owner、动作与复审日期三缺一不入册。
3. 关闭验证看效果，不看动作是否完成。无法立即验证的进入观察期。
4. 三条扫描线覆盖技术、业务与组织。扫描产出必须汇入登记册。
5. 审计配合按授权接口、口径一致与证据索引执行。留痕在平时，不突击补材料。
6. 数据使用先确认级别、环境与用途。进 AI 工具前过边界，脱敏按清单验证。
7. 验收看机制能否应对抽查。反复出现的执行问题进入复盘流程。
