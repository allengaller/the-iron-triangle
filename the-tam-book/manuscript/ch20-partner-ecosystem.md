# 第 20 章　伙伴与供应链生态

> 金融级大项目通常不是单一厂商交付。核心系统可能由自研加独立软件开发商（Independent Software Vendor，ISV）组成。系统可能运行在多家云上。链路可能连接运营商专线。底层还有硬件厂商。总集成商在最上层。TAM 是客户技术成功的操盘手。操盘手不能只看自己的一段链路。本章解决三件事。识别生态与位置。建立协同机制。处理接缝争议。本章为 How-to。岗位边界见[第 2 章](ch02-role-boundary-map.md)，内部协同见[第 19 章](ch19-internal-collaboration.md)。

## 20.1 前置条件与目标

生态动作开始前，先确认以下输入。缺项时先补齐，或把缺项登记为风险。

| 前置条件 | 检查内容 | 缺项处理 |
| --- | --- | --- |
| 生态清单 | 各方名称、范围与界面 | 向 PM 与商务确认 |
| 接缝清单 | 跨厂商系统接口与责任接口 | 按[第 16 章](ch16-project-change-practical.md)补齐 |
| 责任矩阵 | 接口级责任分配矩阵（RACI）与兜底规则 | 与各方书面确认 |
| 接口人 | 技术与管理联系人 | 进入关键人地图 |
| 升级通道 | 三通道互认与时限 | 用[模板 06](../templates/06-major-incident-communication-matrix.md)对齐 |
| 演练安排 | 联合演练场景与频次 | 按[附录 K](appx-k-incident-emergency-drill-standard.md)确认 |
| 信息互通 | 版本、生命周期终止（End of Life，EOL）与通告机制 | 先建最小清单 |
| 我方位置 | 总集、分包或平级 | 与商务口径确认 |

目标产物有五项。生态清单、接缝清单、责任矩阵、协同机制记录、争议处理记录。

| 目标 | 完成标志 | 主要证据 |
| --- | --- | --- |
| 生态可见 | 各方角色与商业模式说得清 | 生态清单 |
| 接缝可控 | 每个接口有责任人与验证方式 | 责任矩阵 |
| 协同运行 | 对齐会、演练与互通在跑 | 会议与演练记录 |
| 争议可收敛 | 争议有事实包和结论 | 联合测试与会签 |
| 客户界面清晰 | 客户知道统一接口 | 沟通记录 |

### 20.1.1 责任矩阵与生态清单

责任矩阵应写到接口级。每条接口记录四方信息。实现方、验证方、兜底方与客户确认方。矩阵可复用[第 16 章](ch16-project-change-practical.md)的接口责任模板。

生态清单至少包含七个字段。这些字段让协同不依赖个人记忆。

| 字段 | 内容 | 常见缺失 |
| --- | --- | --- |
| 厂商与产品 | 名称、版本与覆盖范围 | 只写厂商，不写组件 |
| 商务关系 | 合同主体与总集结构 | 技术清单与商务结构脱节 |
| 责任边界 | 自家范围与接口责任 | 边界只到系统级 |
| 接口人 | 技术与管理联系人和替班 | 只有一个联系人 |
| 升级通道 | 通报路径、时限与授权 | 出事后才找路径 |
| 关键依赖 | 上游容量、证书、线路与许可 | 忽略隐性依赖 |
| 生命周期 | 支持状态与 EOL 时间 | 只记录现版本 |

清单按季度刷新。重大变更、换厂商或换接口人时立即刷新。

## 20.2 操作一：识别生态与位置

### 20.2.1 角色与利益逻辑

理解各方靠什么赚钱，是预判行为的基础。客户体验的是整条链路，故障时客户不会先问是谁家的问题。

| 角色 | 商业模式 | 行为特征 | 协同重点 |
| --- | --- | --- | --- |
| 总集成商（SI） | 项目交付与人头 | 倾向控制客户界面 | 明确客户界面与信息权 |
| ISV | 软件授权与实施 | 关注应用稳定 | 应用与平台边界 |
| 云与平台厂商 | 用量订阅 | 关注消费与续费 | 容量、成本与服务等级协议（SLA） |
| 硬件厂商 | 设备与维保 | 关注保修边界 | 备件、响应与生命周期 |
| 运营商 | 带宽订阅 | 关注线路定界 | 定界工具与联合测试 |
| 外包人力 | 人天计费 | 关注工作量确认 | 交付物与验收口径 |

这张表用于识局，不用于贴标签。同一角色在不同项目中可能表现不同。协同重点要写进责任矩阵。

### 20.2.2 三种位置与打法

我方在生态中的位置决定责任形态。位置有三种：总集、分包、平级。

| 位置 | 责任内核 | TAM 动作 | 常见风险 |
| --- | --- | --- | --- |
| 总集 | 对客户最终技术成功负责 | 对分包建立技术治理；客户沟通由我方收口 | 无原则兜底 |
| 分包 | 对本厂范围负责 | 责任矩阵到接口级；建立直达客户的技术意见通道 | 总集过滤信息 |
| 平级 | 无合同支配关系 | 补齐端到端的缝；建立对等接口 | 责任悬空 |

**总集时，管分包如管自己。** 接口规范、联合评审、统一监控和联合演练都要覆盖分包。分包出问题时，对客户先恢复，再内部分界。危机纪律见[第 18 章](ch18-escalation-crisis.md)。

**分包时，守专业独立。** 本厂责任不外包给总集。技术意见要有直达客户的通道，避免转述失真。证据用日志、协议文档与联合测试说话。

**平级时，主动补缝。** 没有一方天然管端到端。先共同确认接缝，再约定临时看护与升级规则。不要等待合同自动解决责任。

### 20.2.3 多云场景的特殊规则

多云是金融客户的常见形态。行业约束见[第 22 章](ch22-financial-industry.md)，服务质量边界见[附录 P](appx-p-tam-service-quality-standard-public-cloud.md)与[附录 Q](appx-q-tam-service-quality-standard-dedicated-cloud.md)。

1. 跨云责任边界书面化。写清谁监控、谁定界、谁触发切换。
2. 给客户统一视图。客户要的是一个大盘，不是多个控制台。
3. 数据面与管控面分开评审。
4. 跨云容灾切换至少每年演练一次。
5. 不为其他云的 SLA 背书。只承担约定接口责任。

## 20.3 操作二：建立生态协同机制

生态协同不是额外外交。它是技术成功的延伸。平时机制有四件。

### 20.3.1 接口人对齐

1. 列出各方技术接口人与管理接口人。
2. 核对联系方式、替班与升级权限。
3. 将外部接口人补进[模板 11](../templates/11-key-person-map-canvas.md)的扩展列。
4. 每季度刷新一次。人员变动时即时更新。

接口人不只写给内部看。必要时与对方互认，避免出事时找不到人。

### 20.3.2 接口规范书面化

接口规范包括两部分。技术接口写协议、版本、容量与时限。流程接口写定级、升级、通报与复盘接口。

| 接口类型 | 必写内容 | 常见缺口 |
| --- | --- | --- |
| 技术接口 | 协议、版本、容量、兼容性 | 只画图，不写限额 |
| 流程接口 | 事件定级、升级、通报、演练 | 出事后才临时商量 |

接口变更要走共同评审。变更影响、兼容性与回退方式同步记录。

### 20.3.3 常见接缝与必备约定

不同接缝有不同的失效方式。接口规范要落到具体约定，不能只写“保持沟通”。

| 接缝类型 | 必备约定 | 常见事故 |
| --- | --- | --- |
| API 调用 | 版本、超时、重试、限流与兼容窗口 | 升级后旧版本不可用 |
| 数据同步 | 口径、幂等、对账与失败重放 | 数据不一致反复出现 |
| 网络链路 | 双路由、切换判据与定界工具 | 单线中断造成全局感知 |
| 联合变更 | 变更日历、顺序与回退联动 | 各方各自变更，链路断裂 |
| 监控告警 | 指标归属、阈值与通知对象 | 告警进入无人认领区 |
| 备份恢复 | 责任方、恢复验证与跨方依赖 | 只做备份，不验恢复 |

这张表用于接口评审。对已存在的接缝逐项核对。缺项时先补约定，再纳入风险登记册。

### 20.3.4 联合治理与对齐会

1. 建立跨厂商技术对齐会，建议每月一次。
2. 议题聚焦接缝：接口变更、联合发布、相互依赖的生命周期状态。
3. 共享一份脱敏风险登记册。各方只写影响链路的条目。
4. 会议输出进入风险登记册和行动台账。
5. 连续两次无产出时，重新定义议程或升级治理层级。

联合治理的目的是减少信息差。不要把对齐会开成各方汇报会。

### 20.3.5 联合演练

演练频次按[附录 K](appx-k-incident-emergency-drill-standard.md)执行。重保联动见[第 24 章](ch24-major-assurance.md)。

1. 优先演练接缝故障。单厂商内部故障不等于链路故障。
2. 场景包括接口超时、数据不一致、线路中断、跨云切换。
3. 演练前确认各方可观测与可操作范围。
4. 演练后输出时间线、卡点与整改项。
5. 整改项进入登记册并指定 Owner。

没有演练过的接缝预案，只能视为假设。

### 20.3.6 信息互通与通告

1. 建立版本路线图与生命周期状态互通清单。
2. 约定重大通告的通报对象与时限。
3. 我方通告体系按[附录 F](appx-f-cloud-vendor-notices-2026.md)维护，对外输出同理。
4. 收到外部通告后，评估对客户链路的影响。
5. 影响客户的部分先转译，再通报。

很多接缝事故源于不知道对方要变。信息互通是成本较低的预防动作。

## 20.4 操作三：处理接缝争议

### 20.4.1 处理步骤

1. **稳住客户界面**：先说明已知事实、当前动作与下次更新时间。
2. **事实先行**：收集日志、协议、配置、变更记录与联合测试结果。
3. **组织联合验证**：在共同可见环境复现，减少立场争论。
4. **形成事实包**：写现象、时间线、证据与已排除项。
5. **对照责任矩阵**：能归位的按矩阵执行，不能归位的进入仲裁。
6. **给出选项与代价**：向客户说明可行方案与影响。
7. **记录结论**：责任归属、临时看护与后续动作留痕。

### 20.4.2 冲突四纪律

生态冲突常见四类：责任推诿、资源争抢、方案分歧、商务利益。四条纪律如下。

1. **客户利益优先，但不当律师**。为客户争取技术结果。不替客户打责任官司。
2. **当证人，不当判官**：提供证据与事实。责任裁决交给矩阵、合同或客户授权。
3. **认己锅，不甩人锅**：自家问题按[第 9 章](ch09-relationship-management.md)纪律承认、补救、再解释。
4. **扯皮抬商务层**：技术事实收敛不了时，升级到商务与合同通道。不陷入反复立场战。

### 20.4.3 商务升级与记录

技术仲裁有时无法解决商务分歧。此时技术侧要做三件事，而不是继续争执。

1. 冻结技术事实包。写清证据、时间线、已排除项和当前影响。
2. 写明可选方案与代价。包括恢复优先方案、临时绕行方案和责任待定方案。
3. 移交商务通道。说明技术约束、客户影响和建议决策时点。

移交记录要完整。记录移交对象、时间、材料版本和接收确认。商务结论回传后，技术侧更新责任矩阵和整改项。

生态争议的档案有三类去向。时间线进入事件复盘。接口缺陷进入产品反馈。责任缺口进入治理改进。

### 20.4.4 立场一句话

对事实负责，对客户尽责，对伙伴留路。

不为项目配合任何违规动作。包括帮客户绕过审批，或替别家签认未验证内容。合规边界见[第 14 章](ch14-risk-compliance-practical.md)。

## 20.5 验收标准

| 验收项 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 生态清单 | 角色、界面与位置清晰 | 抽查清单与商务口径 |
| 接缝责任 | 接口级责任矩阵会签 | 核对矩阵与版本 |
| 协同机制 | 对齐会与行动项正常运行 | 核对会议记录 |
| 联合演练 | 至少覆盖一个接缝场景 | 核对演练记录 |
| 信息互通 | 版本、EOL 与通告有机制 | 抽查互通记录 |
| 争议处理 | 争议有事实包与结论 | 抽查最近争议 |
| 客户界面 | 客户知道统一接口与升级路径 | 访谈客户接口人 |

验收失败时先修机制。接缝责任缺失与演练未覆盖属于关键项。未修复前不得视为合格。

## 20.6 执行故障排查

| 症状 | 常见原因 | 处理动作 |
| --- | --- | --- |
| 故障时找不到责任方 | 接缝清单或矩阵缺失 | 补齐矩阵并会签 |
| 各方互相等待 | 平级位置无牵头规则 | 约定临时看护与升级 |
| 客户收到矛盾信息 | 通报接口未收口 | 明确统一发声口 |
| 对齐会无产出 | 议题宽泛或无人决策 | 聚焦接缝，绑定行动项 |
| 演练只演自己 | 场景设计缺接缝 | 增加跨厂商故障场景 |
| 争议反复拉扯 | 缺事实包或矩阵过粗 | 补联合验证与接口级矩阵 |
| 外部接口人失联 | 名单过期或无替班 | 刷新名单并互认升级通道 |

反复出现的生态问题进入复盘流程。

## 20.7 常见误区

1. **只护自家**：局部最优损害客户全局。客户记住的是链路谁帮他打通。
2. **无原则兜底**：把别家问题全部揽下。边界糊掉后，出事时更难收敛。
3. **把生态推给商务**：合同管商务关系。技术治理与接口规范仍需要 TAM 推动。
4. **把识局当贴标签**：角色模式用于预判，不用于预设敌意。
5. **只演练自家产品**：接缝没有演练，预案就不完整。

## 20.8 执行检查清单

- [ ] 生态清单在手，各方商业模式与界面说得清
- [ ] 我方位置明确，总集、分包或平级打法在执行
- [ ] 接缝清单明确，接口级责任矩阵已会签
- [ ] 外部接口人进入关键人地图并定期刷新
- [ ] 联合对齐会在运行，行动项有闭环
- [ ] 联合演练覆盖过至少一个接缝故障
- [ ] 版本、EOL 与重大通告有互通机制
- [ ] 最近一次争议用事实包收敛并留痕
- [ ] 冲突处理遵守四纪律，未把技术争议变立场战

**本章要点回顾**

3. 三种位置三套打法。总集管分包如管自己，分包守专业独立，平级补端到端的缝。
