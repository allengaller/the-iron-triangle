# 附录 AC　SRE/CRE 工程纵深

## AC.2 操作一：SLI/SLO 与错误预算政策

### 定义速查

- **服务等级指标（Service Level Indicator，SLI）**：服务质量的量化测量口径。取用户旅程上的关键指标；
- **服务等级目标（Service Level Objective，SLO）**：SLI 加目标值加时间窗口；
- **错误预算（error budget）**：`1 − SLO` 的容忍额度。例：SLO 99.9%、窗口 30 天，预算约 43 分钟。

### SLO 与 SLA 别混

| | SLO | SLA |
| --- | --- | --- |
| 性质 | 工程内部目标 | 对客户的合同承诺 |
| 违约后果 | 冻结非关键变更 | SLA Credit（第 26 章口径） |
| 谁定 | 工程与服务团队 | 商务与客户共同签署 |

### 操作步骤

1. 选 SLI。只选用户旅程上的关键指标。不要把监控项全搬上来。
2. 定 SLO。目标值加时间窗口。目标值建议按业务校准。
3. 算错误预算。写清分子分母，口径与第 26 章一致。
4. 定烧率（burn rate）告警。快档抓突发，慢档抓慢性劣化。阈值建议按业务校准。
5. 定预算行动机制。预算耗尽，冻结非关键变更。预算充裕，发布节奏可加速。
6. 政策书面化。与客户和内部团队对齐后归档。

### 金融级增量

- 监管刚性窗口（决算、报送）的 SLO 策略事前写明。豁免与否，合同和预案里说清楚；
- 错误预算是沟通与优先级工具，不是免责牌。监管义务不因预算耗尽而豁免；
- 客户侧无控制权时，预算消耗数据可向客户高层出示。用于争取变更冻结（[第 7+ 章](ch07-practical.md)高层对话）。

### 预期结果

SLO 有书面政策。预算可算、可查、可行动。烧率告警分快慢两档。

### 常见错误

- 把监控项当 SLI。指标一大堆，没人看。
- SLO 定成愿望清单。没有取数支撑。
- 预算只算不用。耗尽了照样发版。

## AC.3 操作二：On-Call 体系设计

### 操作步骤

1. **排班**：主备双岗，与[附录 I](appx-i-on-duty-standard.md) 同源。班次时长与轮换周期建议按业务校准。
2. **上岗门槛**：值班认证走[附录 J](appx-j-enablement-training-standard.md) 三段式。未认证不上岗。
3. **告警质量前置**：接[第 23 章](ch23-service-model-evolution.md)降噪红线。低频高危永不静默。
4. **升级路径**：升级矩阵用[模板 06](../templates/06-major-incident-communication-matrix.md)。首响时限按[附录 B](appx-b-tam-process-system.md) B.3.4。
5. **疲劳管理**：连续夜班上限与强制休息按[附录 S](appx-s-overtime-compoff-standard.md)。疲劳是排班问题，不是态度问题。
6. **交接**：书面交接三要素——未闭环事件、当日变更、未清零告警（附录 B B.3.9）。无口头交接。

### 预期结果

轮换可执行、认证上岗、升级可达、交接书面。值班人不靠硬扛。

### 常见错误

- 排班表上有名字，实际一个人扛。
- 告警不分级，夜里全靠人肉过滤。
- 交接靠嘴。上一班的坑下一班再踩一遍。

## AC.4 操作三：Toil 治理

### 定义五特征

琐事（Toil）指满足五个特征的工作。手动、重复、可自动化、无持久价值、随服务规模线性增长。

### 操作步骤

1. 记录两周。把每天的手动重复动作记进 Toil 台账。
2. 算占比。每周 Toil 工时占总工时的比例。
3. 定削减目标。占比与目标值建议按业务校准。
4. 削减路径优先级：先自动化，再用 AI 杠杆（[第 22 章](ch22-ai-for-tam.md)），最后才谈加人。
5. 每季度复核台账。消灭一类，补录一类。

### 预期结果

Toil 占比可算。削减目标书面化。台账逐季变短。

### 常见错误

- 不记录，凭感觉说“很忙”。
- 把高价值判断工作当 Toil 自动化掉。
- 自动化了没人维护，脚本本身成了新 Toil。

## AC.5 操作四：演练与复盘深度

### 操作步骤

1. **不透题演练**：故障注入按[附录 K](appx-k-incident-emergency-drill-standard.md) 三级演练走。不透题是红线。
2. **Wheel of Misfortune**：桌面推演随机抽故障模式库场景。考察判断链，不考察背题。
3. **复盘深度**：按[附录 R](appx-r-problem-retrospective-standard.md) 三级复盘。对事不对人三纪律。
4. **问责到流程**：金融级口径，问责不止到人，要到流程（[第 19 章](ch19-financial-incident.md)）。
5. **改进闭环**：改进项验证有效才算闭环。同步进风险登记册。

### 预期结果

演练有真实难度。复盘能挖到流程层。改进项闭环可验证。

### 常见错误

- 演练变表演。剧本提前剧透。
- 复盘停在“加强监控”。没有流程改进。
- 改进项没人跟。半年后同一坑再掉一次。

## AC.6 验收标准

| 验收项 | 通过标准 | 验证方式 |
| --- | --- | --- |
| SLO 政策 | 书面化、口径同第 26 章 | 核对政策文档 |
| 烧率告警 | 快慢两档就位 | 核对告警配置 |
| 预算行动 | 耗尽冻结机制可执行 | 抽查行动记录 |
| 值班体系 | 主备双岗、认证上岗 | 核对排班与认证 |
| 交接 | 书面三要素齐全 | 抽查交接记录 |
| Toil 台账 | 占比可算、目标明确 | 核对台账 |
| 演练深度 | 不透题、考察判断链 | 核对演练记录 |
| 复盘深度 | 挖到流程层、改进闭环 | 核对复盘报告 |

关键项是 SLO 政策、值班体系和复盘深度。任一关键项未通过，工程纵深不得视为合格。

## AC.7 执行故障排查

| 症状 | 常见原因 | 处理动作 |
| --- | --- | --- |
| SLO 没人认 | 只工程定，业务没参与 | 拉业务一起校准目标 |
| 预算形同虚设 | 无行动机制 | 补“耗尽冻结”条款 |
| 值班离职率高 | 排班失衡或告警噪声 | 接附录 S 整改排班、接 ch23 降噪 |
| 交接事故频发 | 口头交接 | 强制书面三要素 |
| Toil 越治越多 | 自动化无人维护 | 自动化纳入台账管理 |
| 演练无效果 | 剧本提前透题 | 改不透题红线 |
| 复盘流于形式 | 停在技术层 | 强制防线四问（模板 07） |

反复出现的问题进入复盘流程（[附录 R](appx-r-problem-retrospective-standard.md)）。

---

**本附录要点回顾**

1. SLO 是工程目标，SLA 是合同承诺。别混，也别互相顶替。
2. 错误预算 = 1 − SLO。只算不用等于没算。耗尽就冻结非关键变更。
3. On-Call 四件套：主备双岗、认证上岗、告警降噪、书面交接。疲劳是排班问题。
4. Toil 按五特征识别。先自动化，再 AI 杠杆，最后才加人。
5. 演练不透题，复盘到流程，改进要闭环。工程纵深的终点是可验证的改进。
