# 第 27 章　护航 AI 工作负载

> 客户的大语言模型（Large Language Model，LLM）客服正在进入生产链路。投研助手和信贷审核智能体（Agent）也在进入生产链路。TAM 的任务不是训练模型。TAM 要让工作负载可控上线。TAM 也要让它们可观测运行、可降级恢复、可审计追溯。本章解决六类操作。建立负载清单。治理容量供给。治理推理成本。执行模型闸门。评审检索增强、微调与 Agent。补充重保增量。本章为 How-to。传统架构评审见[第 5 章](ch05-technical-depth.md)，TAM 自用 AI 见[第 28 章](ch28-ai-for-tam.md)，模型风险治理见[第 31 章](ch31-ai-risk-governance.md)。

## 27.1 前置条件与目标

AI 工作负载进入生产前，先确认以下输入。缺项时先补齐，或登记为上线风险。

| 前置条件 | 检查内容 | 缺项处理 |
| --- | --- | --- |
| 业务场景 | 用户、输入、输出、业务决策和影响面 | 与业务 Owner 确认 |
| 负载清单 | 模型、版本、提供方、链路和环境 | 建立 AI 负载台账 |
| 数据边界 | 数据分级、授权、脱敏和禁用场景 | 按[第 14 章](ch14-risk-compliance-practical.md)、[第 31 章](ch31-ai-risk-governance.md)确认 |
| 架构图 | 模型、检索、工具、缓存、网关和人工节点 | 纳入[模板 03](../templates/03-architecture-review-checklist.md) |
| 容量基线 | 并发、上下文长度、生成 token 和峰值模型 | 按[第 5 章](ch05-technical-depth.md)建模 |
| 成本口径 | 单位调用、单位业务和预算阈值 | 建立推理成本视图 |
| 评估集 | 业务样本、判定标准和红线指标 | 由业务侧参与确认 |
| 变更窗口 | 模型、提示词、检索配置和知识库变更 | 纳入变更治理 |
| 人工节点 | 复核、接管、否决和紧急停用 | 书面指定岗位 |

完成标志有六项。负载可盘点。容量可测算。成本可解释。模型可回退。风险可审计。重保可增量。

| 目标 | 完成标志 | 主要证据 |
| --- | --- | --- |
| 负载可见 | 每个 AI 负载有 Owner 和版本 | 负载台账 |
| 容量可控 | 峰值模型和排队策略通过评审 | 容量评审记录 |
| 成本可控 | 单位成本进入监控和报告 | 成本看板 |
| 上线可控 | 模型变更通过闸门 | 评估与回退记录 |
| 架构可控 | 检索增强与 Agent 评审通过 | 评审结论 |
| 重保可控 | AI 增量项纳入保障清单 | 重保 Checklist |

### 27.1.1 与传统负载的关键区别

| 维度 | 传统系统 | AI 工作负载 |
| --- | --- | --- |
| 故障形态 | 错误通常可复现、可定位 | 输出可能是概率事件，“昨天对今天错” |
| 容量单位 | QPS、CPU、内存 | token 吞吐、上下文长度、GPU 数量与型号 |
| 成本曲线 | 常随容量阶梯变化 | 近似随 token 或调用量放大 |
| 变更含义 | 代码、配置和版本变更 | 模型、提示词、知识库和检索配置也是变更 |
| 回退含义 | 回滚代码版本 | 回滚模型或配置，并验证输出质量 |
| 服务承诺 | 可用性、延迟 | 可用性、延迟，加输出质量水位 |

核心原则是把模型当作新型基础设施组件治理。它要进入变更管理、容量规划、上线闸门和重保。判据要为输出不确定性做扩展。

## 27.2 操作一：建立 AI 负载清单

### 27.2.1 负载分类

| 类型 | 典型形态 | 护航重点 |
| --- | --- | --- |
| 生成服务 | 文案、摘要、知识问答 | 输出质量、引用与拒答策略 |
| 检索增强服务 | 企业知识库问答、投研助手 | 权限、知识保鲜和召回质量 |
| 决策辅助 | 信贷初审、理赔辅助、合规筛查 | 人工节点、可解释性和审计 |
| Agent | 调用工具、执行流程或自动处理工单 | 权限最小化、循环防护和全链路日志 |
| 批处理 | 文档抽取、批量摘要和标签化 | 队列、成本和失败重放 |

### 27.2.2 台账字段

| 字段 | 说明 | 常见缺失 |
| --- | --- | --- |
| 业务场景 | 服务什么业务决策或流程 | 只写“智能问答” |
| 模型与版本 | 基座、微调版本、部署版本 | 只写模型名，不写版本 |
| 提供方 | 自建、云服务或第三方模型 | 缺少依赖层级 |
| 数据边界 | 输入、输出、训练和留存的授权范围 | 未关联数据分级 |
| 关键链路 | 上游系统、模型服务和下游动作 | 缺少工具调用与人工节点 |
| 服务目标 | 可用性、延迟、质量和成本目标 | 只有可用性 |
| Owner | 业务、技术、安全和厂商接口 | 只有技术 Owner |
| 变更范围 | 模型、提示词、知识库和检索配置 | 提示词不入版本管理 |

### 27.2.3 操作步骤

1. 盘点生产、试点和影子运行的 AI 负载。
2. 按“模型—检索—工具—人工节点”补全链路。
3. 为每个负载指定业务、技术和安全 Owner。
4. 关联数据分级、授权范围和禁用场景。
5. 标记影响面：客户权益、资金、监管报送或内部效率。
6. 登记模型版本、提供方、部署位置和回退对象。
7. 将提示词、检索配置、知识库和评估集纳入版本管理。
8. 每月刷新台账。版本、Owner 或链路变化时即时刷新。

## 27.3 操作二：治理 GPU 容量与供给

### 27.3.1 容量模型

推理容量不是只看 GPU 数量。它至少受五个变量影响。变量是并发会话、上下文长度、生成长度、延迟目标和模型吞吐。

可用简式表达：

> 推理容量 ≈ 并发 × 上下文长度 × 生成长度 ÷ 单卡吞吐

举例只用于说明量级。峰值 200 并发，平均上下文 4K token，要求首 token 延迟低于 1 秒。先按所选模型的单卡吞吐折算 GPU 数量，再乘 1.5–2 倍冗余系数。真实值必须以压测和厂商实测为准。

| 容量项 | 检查内容 | 常见漏项 |
| --- | --- | --- |
| 峰值模型 | 工作日、营销日、批处理和突发查询 | 只按平均会话估算 |
| 上下文 | 历史轮次、系统提示和检索片段 | 检索片段挤占上下文 |
| 并发 | 在线用户、定时任务和 Agent 并发 | Agent 重试放大并发 |
| 吞吐 | 单卡、单实例和批量推理吞吐 | 用理论值替代实测值 |
| 排队 | 队列长度、等待时限和拒绝策略 | 只报忙，没有降级路径 |
| 供给 | 配额、区域、机型和采购周期 | 没有“拿不到卡”的预案 |

### 27.3.2 操作步骤

1. 从业务日历和历史日志提取峰值场景。
2. 与业务方确认并发、上下文和生成长度。
3. 按模型和部署形态获取单卡或单实例实测吞吐。
4. 计算容量缺口，明确扩容、排队或降级策略。
5. 区分训练与推理资源。共用 GPU 池时确认隔离策略。
6. 为排队、降级和拒绝设置业务可见规则。
7. 将配额、机型、区域和替代供给写入风险登记册。
8. 季度复核容量模型。模型、提示词或流量结构变化时立即复核。

### 27.3.3 供给风险

GPU 配额、机型和区域供给可能受限。采购与开通周期也可能较长。具体动态以厂商最新通告为准，见[附录 F](appx-f-cloud-vendor-notices-2026.md)。

容量规划必须回答“拿不到卡怎么办”。可选路径有四类。它们是多区域配额、多供应商、模型降级链和批处理错峰。必要时还可启用业务限流。每个路径都要有触发条件与授权人。

## 27.4 操作三：治理推理成本

### 27.4.1 成本对象

推理成本会随业务量放大。它不像传统容量那样只靠规模摊薄。TAM 要把技术消耗翻译成业务口径，方法见[第 7 章](ch07-business-insight.md)。

| 成本对象 | 示例 | 治理问题 |
| --- | --- | --- |
| 千次对话 | 客服会话、知识问答 | 单次会话是否带过多历史 |
| 单笔业务 | 一次信贷初审或一份报告 | 人工与 AI 的组合成本 |
| 每文档 | 抽取、摘要、翻译或审核 | 失败重试是否重复计费 |
| 每 Agent 任务 | 一次工单处理或流程执行 | 工具调用和循环是否失控 |
| 每模型版本 | 基座、微调或小模型路由 | 新版本是否改变单位成本 |

### 27.4.2 操作步骤

1. 定义单位成本口径。分子、分母、时间窗和排除项都要写清。
2. 将 token 消耗、调用次数和费用接入监控。
3. 为每个业务场景建立成本基线和异常阈值。
4. 把异常上升按事件处理，不只在月报中解释。
5. 每月输出单位成本趋势、异常事件和优化动作。
6. 将成本趋势纳入季度业务回顾（Quarterly Business Review，QBR）。治理机制见[第 11 章](ch11-service-governance.md)，商业呈现见[第 21 章](ch21-commercial-synergy.md)。
7. 每半年复核自建 GPU 与按调用计费的平衡点。业务量、模型版本或价格变化后立即复核。

### 27.4.3 降本杠杆

| 杠杆 | 适用场景 | 风险控制 |
| --- | --- | --- |
| 大小模型路由 | 简单问题走小模型 | 建立路由规则和抽检 |
| 语义缓存 | 高频相似问题 | 缓存按权限和数据时效隔离 |
| 提示词瘦身 | 系统提示和检索片段过长 | 版本化并回归评估 |
| 上下文裁剪 | 历史轮次和检索内容过长 | 保留关键事实与引用 |
| 批处理错峰 | 非实时文档处理 | 设置队列、失败重放和成本上限 |
| 量化部署 | 自建推理且质量可接受 | 上线前对比评估集结果 |

云成本优化（FinOps）不是只做降价。它要同时回答三个问题。成本花在哪个业务场景？是否带来了可验证价值？异常消耗由谁处理？

## 27.5 操作四：执行模型评估与上线闸门

### 27.5.1 模型版本即变更

模型升级、微调和提示词调整属于变更对象。知识库重组和检索配置变化也属于变更对象。它们应进入变更治理。治理机制见[第 11 章](ch11-service-governance.md)，上线闸门见[第 16 章](ch16-project-change-practical.md)。

| 变更对象 | 风险 | 必备证据 |
| --- | --- | --- |
| 基座模型 | 输出分布和能力边界变化 | 评估集回归与安全抽检 |
| 微调版本 | 过拟合、数据偏差和版权合规 | 训练数据说明与评估报告 |
| 提示词 | 行为、格式和安全边界变化 | 版本记录与回归结果 |
| 知识库 | 过期、越权和低质量内容 | 更新记录与召回抽测 |
| 检索配置 | 召回范围和权限变化 | 权限测试与质量抽测 |
| 工具权限 | Agent 可执行动作变化 | 权限矩阵与审计验证 |

### 27.5.2 上线闸门四判据

| 判据 | 通过要求 | 证据 |
| --- | --- | --- |
| 离线评估过线 | 业务评估集达到约定红线，且不劣于现版本 | 评估报告 |
| 幻觉与拒答策略明确 | 错误答案、拒答和人工兜底的代价由业务确认 | 策略签字 |
| 降级方案实测 | 主模型到备模型、规则引擎或人工通道可切换 | 演练记录 |
| 人工接管预算 | 转人工比例与坐席能力匹配 | 容量测算 |

评估集不能只有技术题库。它应包含客户业务样本、边界案例、对抗问题和历史失败场景。业务侧应参与样本确认和判定标准签署。

### 27.5.3 服务承诺写法

传统可用性指标不足以约束 AI 输出。服务等级协议（Service Level Agreement，SLA）应增加输出质量维度。质量指标要写清测量方式。

| 指标 | 示例口径 | 必写内容 |
| --- | --- | --- |
| 抽检合格率 | 周期抽检合格比例 | 样本量、抽检人和判定标准 |
| 人工接管率 | 转人工比例 | 分母口径与统计周期 |
| 高危错误 | 资损、合规或权益类错误 | 定义、阈值和处理流程 |
| 引用可回溯率 | 回答附可核验引用的比例 | 引用粒度与核验方法 |
| 成本上限 | 单位调用或周期预算 | 超限后的降级动作 |

质量水位不达标时的动作也要写清。可以降流量、切备用模型、扩大人工复核或暂停上线。

### 27.5.4 操作步骤

1. 确认变更对象和影响链路。
2. 冻结评估集版本，业务侧确认判定标准。
3. 执行离线评估、安全抽检和回归对比。
4. 评审幻觉、拒答、引用和人工兜底策略。
5. 实测降级链路，记录切换耗时和业务验证结果。
6. 核对人工接管预算和坐席排班。
7. 上线后设置观察期，对比评估结果与生产抽检。
8. 不达标即回退，并记录原因与复核时点。

## 27.6 操作五：评审检索增强、微调与 Agent

### 27.6.1 检索增强服务评审

检索增强生成（Retrieval-Augmented Generation，RAG）也有常见风险。风险不是“查不到”。更常见的是查到过期、越权或低质量内容。

| 评审项 | 必答问题 | 通过证据 |
| --- | --- | --- |
| 知识来源 | 文档来自哪里，授权是否明确 | 来源清单 |
| 数据边界 | 是否含个人信息、客户数据和敏感商业数据 | 数据分级记录 |
| 权限隔离 | 不同密级是否分区索引，能否召回无权文档 | 越权测试 |
| 知识保鲜 | 更新机制、失效清理和责任人是哪些 | 更新台账 |
| 召回质量 | 如何测召回率、排序和答案支撑 | 评估报告 |
| 引用可回溯 | 回答能否定位到原文片段 | 抽检记录 |
| 变更治理 | 知识库与检索配置是否走变更 | 版本记录 |

RAG 的上线门槛至少有三条。权限测试通过。引用可回溯。知识库变更进入版本管理。

### 27.6.2 微调评审

| 评审项 | 必答问题 | 常见风险 |
| --- | --- | --- |
| 训练数据 | 来源、授权和敏感字段是否清楚 | 使用未授权客户数据 |
| 数据处理 | 清洗、脱敏和样本平衡如何做 | 放大样本偏差 |
| 训练隔离 | 训练、评估和生产环境是否分离 | 生产数据泄漏 |
| 版本管理 | 数据集、超参、产物和评估报告是否关联 | 无法复现 |
| 回退路径 | 能否回到上一版或基座能力 | 只能前滚，不能回退 |
| 基座生命周期 | 基座生命周期终止（End of Life，EOL）后微调产物怎么办 | 迁移造成效果漂移 |

微调不是默认更优。若 RAG 能解决知识更新问题，应先评估 RAG。若必须微调，先确认数据授权、可复现性和长期维护成本。

### 27.6.3 Agent 评审

Agent 风险高于普通生成服务。它可能把错误输出转化为实际动作。评审必须更严。

| 评审项 | 必答问题 | 硬性要求 |
| --- | --- | --- |
| 工具权限 | Agent 能读什么、写什么、执行什么 | 权限最小化 |
| 人工确认 | 写操作、支付、审批和外发是否需人确认 | 关键动作人在回路 |
| 循环防护 | 最大步数、token 预算、超时和熔断如何设置 | 上限写入配置 |
| 失败处理 | 工具失败、部分成功和重复调用如何处理 | 幂等或补偿机制 |
| 审计日志 | 谁触发、输入是什么、调用了什么工具、产生了什么结果 | 全链路留痕 |
| 注入防护 | 外部网页、邮件和文档是否可能携带指令 | 内容隔离与过滤 |
| 紧急停用 | 谁能停用，停用后业务如何接续 | 书面授权和替代流程 |

没有全链路审计日志的 Agent，不得进入金融生产环境。这个门槛不能靠事后补日志满足。

### 27.6.4 操作步骤

1. 读取 AI 负载台账，确认评审范围。
2. 按模板 03 完成传统六维和 AI 专项。
3. 对 RAG 做权限、引用和召回抽测。
4. 对微调核对数据授权、版本链和回退路径。
5. 对 Agent 核对权限矩阵、审计日志和熔断配置。
6. 将风险项写入风险登记册，指定 Owner 和期限。
7. 输出评审结论：通过、带条件通过或不通过。
8. 条件项进入上线闸门，未闭环不得扩量。

## 27.7 操作六：补充 AI 重保增量

AI 负载进入重保时，[第 24 章](ch24-major-assurance.md)的五阶段框架不变。体检和预案要增加专项。

| 增量项 | 检查内容 | 完成证据 |
| --- | --- | --- |
| 模型版本冻结 | 窗口期禁止模型、提示词和检索配置变更 | 冻结记录 |
| 评估集回归 | 冻结前完成回归测试 | 评估报告 |
| GPU 容量锁定 | 配额、实例和备用算力确认 | 资源确认单 |
| 推理降级链 | 主模型、备模型和人工通道实测 | 演练记录 |
| token 异常告警 | 成本与消耗阈值设定 | 告警配置 |
| 第三方依赖 | 模型 API 的限额、限流和支持窗口 | 合同或服务说明 |

### 操作步骤

1. 在重保立项时标记 AI 负载和关键链路。
2. 将模型、提示词、知识库和检索配置纳入冻结范围。
3. 冻结前完成评估集回归和安全抽检。
4. 锁定 GPU、配额、备模型和人工坐席。
5. 实测主模型到备用路径的切换。
6. 设置 token 消耗、错误率和延迟的窗口期阈值。
7. 确认第三方模型或 API 的支持窗口与限流规则。
8. 将六项结果写入重保 Checklist。

## 27.8 验收标准

| 验收项 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 负载清单 | 生产 AI 负载全覆盖，字段完整 | 抽查台账与生产链路 |
| 容量模型 | 峰值、排队和降级策略经评审 | 核对压测与评审记录 |
| 供给预案 | 配额缺口、替代供给和触发条件明确 | 核对风险登记册 |
| 成本治理 | 单位成本可算、可看、可解释 | 核对成本看板 |
| 评估闸门 | 模型变更均有评估和回归证据 | 抽查变更记录 |
| 质量承诺 | SLA 含质量指标与测量口径 | 核对协议草案 |
| 降级链路 | 主模型到备模型或人工实测可切 | 核对演练记录 |
| RAG 控制 | 权限测试、引用回溯和知识保鲜通过 | 核对评审证据 |
| Agent 控制 | 权限最小化、熔断和审计日志通过 | 核对配置与日志 |
| 重保增量 | 六项全部进入重保 Checklist | 核对模板 05 |

关键项包括负载清单、模型闸门、降级链路、RAG 权限和 Agent 审计。任一关键项未通过，不得视为生产护航合格。

## 27.9 执行故障排查

| 症状 | 常见原因 | 处理动作 |
| --- | --- | --- |
| 同一问题昨天对今天错 | 模型、提示词、知识库或检索结果变化 | 核对版本链，复现输入 |
| 评估好但生产差 | 评估集不代表业务样本 | 补业务样本并重新签署判定标准 |
| GPU 排队严重 | 峰值模型漏并发或上下文增长 | 重算容量，启用排队和降级 |
| 推理成本突增 | 重试风暴、循环调用或上下文膨胀 | 定位调用链，设预算与熔断 |
| 回答引用不可回溯 | 检索片段错误或引用生成失真 | 抽测召回，强制原文引用 |
| 知识回答过期 | 知识库无保鲜或更新未走变更 | 建更新台账并补回归 |
| 越权召回 | 索引未按密级隔离 | 停用相关链路，重做权限测试 |
| Agent 执行异常动作 | 工具权限过宽或提示注入 | 停用写操作，收紧权限并审计 |
| 转人工打爆坐席 | 接管率预算缺失 | 限流、扩容坐席或收窄场景 |
| 模型回退失败 | 无版本、无评估或依赖不兼容 | 先降级到人工，补回退演练 |
| 第三方模型不可用 | 配额、限流或生命周期变化 | 启用备模型，登记供给风险 |

反复出现的问题进入复盘流程。模型风险治理细节见[第 31 章](ch31-ai-risk-governance.md)。

## 27.10 常见误区

1. **把模型当普通配置**：只登记名称，不登记版本、数据和回退对象。
2. **把演示效果当生产能力**。演示样本窄，可能未覆盖业务边界和对抗输入。
3. **先上线再算成本**：成本失控后才发现业务价值无法覆盖消耗。
4. **把输出质量留在验收外**。只承诺可用性，不约定抽检合格率和高危错误阈值。
5. **把 RAG 当权限边界**：检索系统不等同于权限系统，越权仍可能发生。
6. **把 Agent 当聊天机器人**：忽略工具权限、写操作、审计和紧急停用。
7. **把回退写成文档**：没有实测的降级链路，不能作为生产承诺。

---

**本章要点回顾**

1. AI 负载要当作新型基础设施组件治理。模型、提示词、知识库和检索配置都是变更对象。
2. 台账先于护航。每个负载要有 Owner、链路、版本、数据边界和服务目标。
3. 容量按并发、上下文、生成长度、延迟和实测吞吐建模。供给风险要有替代路径。
4. 推理成本要进入单位业务口径、监控、异常告警和 QBR。
5. 模型版本变更是系统变更。评估、安全抽检、降级实测和人工接管预算是闸门判据。
6. RAG 的硬门槛是权限隔离、引用可回溯和知识保鲜。
7. Agent 的硬门槛是权限最小化、人在回路、熔断和全链路审计。
8. AI 重保保留五阶段框架。它新增六类增量项。团队要完成模型冻结、评估回归和算力锁定。团队还要完成降级实测、消耗告警和第三方确认。
