# 附录 Y　六维能力训练教程

> 本附录为 Tutorial + How-to 类型：Tutorial 部分是手把手带你走完训练流程（目标、前置、步骤、验证），How-to 部分是每次训练可直接照做的操作动作与验收标准。每节包含训练目标、前置条件、分步操作、验证标准和常见错误。
> 
> **适用对象**：TAM 新人、想从 L1 晋升到 L2-L3 的 TAM、团队负责人（用于带教）。
> **前置条件**：已完成对应章节（ch05-ch10）的 Explanation 阅读，理解"是什么、为什么"。

---

## Y.1 技术纵深训练

### 训练目标

完成本章训练后，你能独立进行一次完整的架构评审，并输出有质量的分级报告。

### 前置条件

- 已阅读第 5 章（技术纵深），理解 T 型结构和常见误区
- 已阅读第 5+ 章（技术纵深实战），掌握操作步骤
- 有一个真实客户场景（可以是内部模拟场景）

### 训练一：建立客户技术档案（2 小时）

**步骤**：

1. 选择一个你负责的客户（或模拟客户）
2. 按以下模板建立档案：
   - 架构图（组件级，含部署形态）
   - 版本台账（在用组件、EOL 日期）
   - 配置基线（关键配置项）
   - 故障史（近 12 个月 RCA 记录）
   - 容量基线（响应时间、吞吐、资源水位）
   - 业务峰值日历（月末、账单日、大促、行情日）
3. 请一位同事审阅档案，确认关键信息完整

**验证标准**：

- [ ] 同事能在 10 分钟内通过档案理解该客户的核心链路
- [ ] 档案中包含至少 3 个已识别的风险项

**常见错误**：

- 档案过于详细：把运维文档直接复制过来，没有提炼
- 档案过于简略：只有架构图，没有版本、容量、故障信息
- 档案不更新：建立后就束之高阁

---

### 训练二：影子评审（3 次 × 2 小时 = 6 小时）

**步骤**：

1. **第 1 次（只听）**：
   - 跟随资深架构师参加一次架构评审
   - 记录评审过程中的关键问题和结论
   - 会后向架构师请教"为什么问这个问题"

2. **第 2 次（记录并复述）**：
   - 再次跟随评审，负责记录
   - 评审结束后，向客户复述评审结论（由架构师补充）
   - 记录自己的复述与架构师结论的差异

3. **第 3 次（主讲一部分）**：
   - 在架构师的指导下，主讲评审中的一个维度（如可用性）
   - 由架构师补充其他维度
   - 评审结束后，请架构师给出反馈

**验证标准**：

- [ ] 能独立复述评审结论，且与架构师结论一致度 > 80%
- [ ] 主讲维度的问题被客户认可为"有价值"

**常见错误**：

- 急于表现自己，打断架构师
- 只记录不思考，没有理解"为什么问这个问题"
- 复述时遗漏风险项的闭环要求

---

### 训练三：建立故障模式库（持续）

**步骤**：

1. 每读到一份 RCA（自己客户的、公司内部的、公开的事后报告），提炼一个模式
2. 按以下格式记录：
   - 模式名称
   - 触发条件
   - 故障表现
   - 根因分析
   - 预防措施
   - 检测方法
3. 每周回顾一次，补充新发现的模式
4. 与团队共建：每月一次团队分享，每人贡献 1-2 个模式

**验证标准**：

- [ ] 个人模式库 ≥ 50 个模式
- [ ] 团队模式库 ≥ 200 个模式
- [ ] 模式库在评审中被引用 ≥ 3 次/月

**常见错误**：

- 只记录现象，不分析根因
- 模式过于具体，无法复用
- 不更新，变成"僵尸库"

---

### 训练四：back-of-envelope 估算练习（每月 1 次）

**步骤**：

1. 找一个真实场景（可以是客户的容量规划需求）
2. 用 back-of-envelope 方法估算容量或可用性
3. 记录估算过程和假设
4. 与实测数据对照，校准估算偏差
5. 记录校准结果，更新"估算直觉"

**验证标准**：

- [ ] 估算结果与实测数据的偏差 < 30%（量级正确）
- [ ] 能在 2 分钟内给出量级估算

**常见错误**：

- 过于追求精确，忘记"量级正确即可"
- 不做校准，估算永远不准
- 只估算不记录，无法形成"估算直觉"

---

### 训练五：一页纸评审输出（每次评审后）

**步骤**：

1. 每次评审后，将结论压缩成一页纸
2. 一页纸必须包含：
   - 风险是什么（一句话）
   - 为什么（因果链）
   - 怎么办（整改建议）
   - 不办的代价（业务影响）
3. 请一位同事审阅，确认"非技术人员也能看懂"

**验证标准**：

- [ ] 每次评审都有一页纸输出
- [ ] 非技术人员能看懂核心结论
- [ ] 一页纸被客户认可并纳入跟踪

**常见错误**：

- 写成技术报告，非技术人员看不懂
- 只写风险，不写"不办的代价"
- 不闭环，写完就完了

---

## Y.2 业务洞察训练

### 训练目标

完成本章训练后，你能将技术指标翻译成业务语言，并建立客户业务地图。

### 前置条件

- 已阅读第 6 章（业务洞察），理解三个层次和常见误区
- 已阅读第 6+ 章（业务洞察实战），掌握操作步骤
- 有一个真实客户（或模拟客户）

### 训练一：业务地图绘制（3 小时）

**步骤**：

1. 选择一个你负责的客户（或模拟客户）
2. 按以下模板绘制业务地图：
   - 行业：银行/证券/保险/支付
   - 业务主线（3-5 条）：核心功能、技术依赖、峰值特征
   - 关键系统：核心系统、渠道、风控、监管报送
   - 业务日历：刚性节点、弹性峰值、内部节奏
3. 与客户技术负责人确认地图准确性
4. 每季度更新一次

**验证标准**：

- [ ] 同事能在 5 分钟内理解该客户的核心业务
- [ ] 地图中包含至少 3 条业务主线和对应的技术依赖
- [ ] 客户确认地图准确性

**常见错误**：

- 地图过于技术化：只有系统清单，没有业务主线
- 地图过于简化：只有业务名称，没有技术依赖
- 不更新：地图建立后不再维护

---

### 训练二：价值翻译练习（每月 2 次）

**步骤**：

1. 从技术报告中选择一个关键指标（如可用性、MTTR、容量）
2. 按以下公式翻译：
   ```
   技术指标 → 业务影响 → 财务影响
   ```
3. 填写价值翻译表：
   | 技术指标 | 业务影响 | 财务影响 | 数据出处 |
   |----------|----------|----------|----------|
4. 请客户确认翻译的准确性
5. 收集反馈，校准翻译方法

**验证标准**：

- [ ] 每个技术指标都能翻译成业务影响
- [ ] 财务影响有数据出处或合理假设
- [ ] 客户认可翻译的准确性

**常见错误**：

- 只翻译到技术层面，没有触及业务影响
- 财务影响没有数据出处，变成"拍脑袋"
- 翻译过于复杂，非技术人员看不懂

---

### 训练三：目标挂靠验证（每季度 1 次）

**步骤**：

1. 获取客户公司战略（年报/年度工作报告）
2. 识别客户科技部的年度目标
3. 列出你当前负责的所有项目
4. 为每个项目找到对应的部门目标
5. 验证链条：问客户"这个项目对部门今年的目标意味着什么？"
6. 标记挂不上的项目（可能是低优先级）

**验证标准**：

- [ ] 每个项目都能一句话说清挂到哪条业务目标
- [ ] 客户 CIO 层面有人能复述你团队带来的业务价值
- [ ] 挂不上的项目不超过 10%

**常见错误**：

- 只关注项目交付，不问业务目标
- 目标挂靠过于牵强，客户不认可
- 不更新：目标变化后不重新验证

---

## Y.3 关系经营训练

### 训练目标

完成本章训练后，你能建立并维护客户关键人地图，管理信任账户，处理冲突。

### 前置条件

- 已阅读第 7 章（关系经营），理解信任账户模型和常见误区
- 已阅读第 7+ 章（关系经营实战），掌握操作步骤
- 有一个真实客户（或模拟客户）

### 训练一：关键人地图绘制（2 小时）

**步骤**：

1. 选择一个你负责的客户（或模拟客户）
2. 按以下模板绘制关键人地图：
   - 列出所有关键人（从项目文档、会议记录、通讯录中提取）
   - 标注三条链：决策链、影响链、防线
   - 评估态度与影响力：支持/中立/反对，高/中/低
   - 标注覆盖频次：每月/每季/半年/年度
   - 识别接班人：每个关键人标注潜在接班人
3. 制定行动计划：空白层就是下季度行动清单

**验证标准**：

- [ ] 地图覆盖决策链、影响链、防线三层
- [ ] 核心客户有三层覆盖，无单点依赖
- [ ] 每个关键人标注了态度和接班人

**常见错误**：

- 只关注决策链，忽视影响链和防线
- 地图过于简化：只有姓名和职位，没有态度和影响力
- 不更新：人员变动后不及时更新

---

### 训练二：信任账户管理（持续）

**步骤**：

1. 建立信任账户台账，记录每次存款和取款
2. 存款操作：
   - 兑现小承诺：说过"明天给你数据"就明天给
   - 先讲坏消息：在客户从别处听到之前主动讲
   - 判断被验证：评审指出的风险被事实验证，书面留痕
   - 为客户挡事：内部协调资源、替客户顶住不合理流程
3. 取款预警：识别并避免以下行为
   - 失约、隐瞒或迟报
   - 让客户在他的领导面前丢脸
   - 越过接口人向其上级告状
   - 为指标好看而操纵数据
4. 每月评估一次账户余额

**验证标准**：

- [ ] 有完整的信任账户台账
- [ ] 存款次数 > 取款次数 × 2
- [ ] 近三个月没有"让客户丢脸"的取款记录

**常见错误**：

- 只记存款不记取款
- 对"让客户丢脸"的严重性认识不足
- 不及时更新台账

---

### 训练三：高层对话模拟（每季度 1 次）

**步骤**：

1. 准备一个真实的汇报场景（如项目进度、风险评估）
2. 按一页纸模板准备汇报材料：
   - 【状态】当前系统可用性 99.95%，满足 SLA。
   - 【风险】核心组件 X 将于 2027-03 EOL，需启动升级评估。
   - 【建议】方案 A/B/C（带代价）
   - 【请求】请本周内确认方案
3. 找一位同事扮演客户高层，进行模拟汇报
4. 收集反馈，改进汇报技巧

**验证标准**：

- [ ] 汇报在一页纸内讲清状态、风险、建议、请求
- [ ] 带了 2-3 个方案及各自代价
- [ ] 模拟汇报后 24 小时内有书面纪要

**常见错误**：

- 技术细节过多，高层听不进去
- 只带问题不带方案
- 会后不闭环

---

## Y.4 服务治理训练

### 训练目标

完成本章训练后，你能制定服务计划、管理 SLA/OLA/XLA、建立例会体系。

### 前置条件

- 已阅读第 8 章（服务治理），理解三层契约和常见误区
- 已阅读第 8+ 章（服务治理实战），掌握操作步骤
- 有一个真实客户（或模拟客户）

### 训练一：服务计划制定（4 小时）

**步骤**：

1. 选择一个你负责的客户（或模拟客户）
2. 收集输入：客户业务目标、系统清单、业务日历、历史服务记录
3. 按以下模板制定服务计划：
   - 服务目标（3-5 条，挂在客户业务目标上）
   - 服务范围（覆盖系统清单 + 明确不覆盖什么）
   - 节奏表（例会、评审、健康检查、重保、QBR 的年度排期）
   - 风险与依赖（初始风险清单）
   - 交付物清单（月报、评审报告、VBR 等，附模板编号）
4. 与客户接口人共同签署

**验证标准**：

- [ ] 服务计划包含目标、范围、节奏、风险、交付物五部分
- [ ] 每个目标都能挂到客户业务目标
- [ ] 客户接口人已签字确认

**常见错误**：

- 目标写成"做好服务工作"式空话
- 范围无界，出事全是你的
- 只有频次没有日期，季度末全堆一起

---

### 训练二：SLA/OLA 谈判模拟（2 小时）

**步骤**：

1. 准备一个真实的 SLA 场景（或模拟场景）
2. 按以下步骤进行谈判：
   - 校核技术可达性：可用性数学、容量规划、架构评审
   - 明确口径：每个指标写清"怎么算、哪取数、谁仲裁"
   - 建立追踪机制：SLA 达成率月报化
3. 找一位同事扮演客户，进行模拟谈判
4. 收集反馈，改进谈判技巧

**验证标准**：

- [ ] SLA 指标技术可达，不是拍脑袋
- [ ] 每个指标都有明确的计算口径和数据源
- [ ] 客户认可 SLA 指标

**常见错误**：

- 承诺 99.99% 却只规划单机房
- 口径不前置，违约时全是扯皮
- 只关注 SLA，忽视 OLA

---

### 训练三：例会体系搭建（3 小时）

**步骤**：

1. 选择一个你负责的客户（或模拟客户）
2. 按以下模板设计例会体系：
   - 值班晨会（每日，重保/驻场期）
   - 服务周会（每周）
   - 服务月会（每月）
   - QBR/EBR（季度）
   - 年度规划会（每年）
3. 为每个会议准备模板化材料
4. 召开第一次月会，记录纪要并跟踪行动项

**验证标准**：

- [ ] 五层节奏完整，不遗漏
- [ ] 每次会议有纪要，行动项责任到人、时间到日
- [ ] 下次会议第一件事是过上次行动项

**常见错误**：

- 会很多，但无纪要不散会
- 纪要不跟踪，行动项悬空
- 会议材料不模板化，每次重新写

---

## Y.5 风险与合规训练

### 训练目标

完成本章训练后，你能建立风险登记册、执行风险扫描、配合审计。

### 前置条件

- 已阅读第 9 章（风险与合规），理解风险与合规的区别和常见误区
- 有一个真实客户（或模拟客户）

### 训练一：风险登记册建立（3 小时）

**步骤**：

1. 选择一个你负责的客户（或模拟客户）
2. 按以下模板建立风险登记册：
   - 风险描述（一句话说清"什么条件下会发生什么坏事"）
   - 类别（技术/业务/组织/合规）
   - 概率 × 影响（高/中/低）
   - Owner（具名负责人）
   - 缓解动作与期限
   - 复审日期
3. 与客户会签重大风险
4. 每月过册

**验证标准**：

- [ ] 登记册包含风险描述、类别、概率、影响、Owner、缓解动作、复审日期
- [ ] 重大风险已双方会签
- [ ] 每条风险都有具名 Owner 和期限

**常见错误**：

- 风险描述写成"系统可能有风险"这种正确的废话
- Owner 写"双方共同关注"等于没人负责
- 没有缓解动作的"风险"只是焦虑，不入册

---

### 训练二：三道扫描线执行（每月 1 次）

**步骤**：

1. **技术扫描**：
   - 容量水位与增长曲线
   - 版本生命周期（EOS/EOL 逼近的组件）
   - 单点与隐性依赖
   - 配置漂移
2. **业务扫描**：
   - 业务日历（决算、大促、监管报送窗口）
   - 冻结纪律、容量余量、值守排班
3. **组织扫描**：
   - 客户关键人变动
   - 预算收缩
   - 决策链重组
   - 你方团队人员流失
4. 记录新发现的风险，入册

**验证标准**：

- [ ] 三道扫描线各有节奏（周快扫、月深扫、季体检）
- [ ] 本月有新风险入册
- [ ] 业务日历上的高危窗口已标注

**常见错误**：

- 只扫技术不扫组织
- 扫描流于形式，不记录新风险
- 不更新风险登记册

---

### 训练三：审计配合模拟（2 小时）

**步骤**：

1. 准备一个模拟审计场景

   - 值班日志

## Y.6 项目与变革管理训练

### 训练目标

完成本章训练后，你能把握项目节奏、执行 Go/No-Go 闸门、推动变革落地。

### 前置条件

- 已阅读第 10 章（项目与变革管理），理解 TAM 在大项目中的位置和常见误区
- 有一个真实项目（或模拟项目）

### 训练一：项目节奏把握（2 小时）

**步骤**：

1. 选择一个你参与的项目（或模拟项目）
2. 按以下模板分析项目阶段：
   - 阶段：立项/设计/开发/测试/上线/稳定化
   - 主要矛盾：每个阶段的主要矛盾是什么
   - TAM 检查点：技术评审、风险登记册、里程碑偏差
3. 识别先行信号：
   - 缺陷重开率上升
   - 变更请求突然增多
   - 决策开始被推迟
   - 关键人开始缺席例会
4. 制定预警机制

**验证标准**：

- [ ] 能准确识别项目当前阶段和主要矛盾
- [ ] 能识别至少 2 个先行信号
- [ ] 有预警机制，能提前 2-4 周预警

**常见错误**：

- 只关注里程碑，不关注先行信号
- 等到里程碑红了才说话
- 对项目阶段的主要矛盾认识不清

---

### 训练二：Go/No-Go 闸门模拟（3 小时）

**步骤**：

1. 准备一个模拟上线场景
2. 按以下模板准备闸门输入：
   - 就绪清单完成情况
   - 风险登记册未关闭项（逐项明确：接受/缓解/阻断）
   - 回退方案实测记录与回退耗时
   - 演练结果与遗留问题
   - 监控与告警就绪（含接收人验证）
   - 值守与升级安排
3. 设定量化判据：
   - 高风险项 = 0
   - 回退实测 ≤ 60 分钟
   - 监控覆盖率 100%
4. 召开模拟闸门评审会，记录决策

**验证标准**：

- [ ] 判据事先量化，不现场议
- [ ] 决策记录书面化，会签留痕
- [ ] 能做出有依据的 No-Go 或带条件 Go

**常见错误**：

- 判据不量化，现场让位于进度
- 怕得罪进度而放水
- 记录不完整，事后扯皮

---

### 训练三：变革推动模拟（2 小时）

**步骤**：

1. 准备一个模拟变革场景（如新系统上线）
2. 识别三类阻力：
   - 不会用：功能闲置、问题重复出现
   - 不愿用：明着用暗着绕回旧流程
   - 不敢用：关键操作仍走旧通道"保险"
3. 为每类阻力制定对策：
   - 赋能与实操培训计划
   - 种子用户机制
   - 陪跑期设计
   - 用数据呈现新流程收益
4. 设计采用率指标和跟踪机制

**验证标准**：

- [ ] 三类阻力都有对应的对策
- [ ] 采用率指标量化可跟踪
- [ ] 变革对策与风险登记册、服务计划联动

**常见错误**：

- 上线即终点，忽视采用率
- 对三类阻力认识不清，一刀切
- 变革对策与项目其他部分脱节

## Y.7 综合演练：六维能力联合评审

### 场景

模拟一个真实的客户项目导入场景，要求综合运用六维能力：

- **技术纵深**：评审客户架构
- **业务洞察**：将技术风险翻译成业务影响
- **关系经营**：识别关键人并制定沟通策略
- **服务治理**：制定服务计划和 SLA
- **风险与合规**：建立风险登记册
- **项目与变革管理**：制定项目计划和里程碑

### 步骤

1. 分组（每组 3-4 人）
2. 分配角色：TAM、客户技术负责人、客户业务负责人、厂商架构师
3. 模拟项目导入会议（2 小时）
4. TAM 组输出：
   - 架构评审报告
   - 风险登记册
   - 服务计划初稿
   - 关键人地图
   - 项目里程碑
5. 评审组（由资深 TAM 组成）评估输出质量

### 验证标准

- [ ] 架构评审报告有分级、有闭环
- [ ] 风险登记册 ≥ 10 条，每条有 Owner 和期限
- [ ] 服务计划包含年度目标、季度动作、月度跟踪
- [ ] 关键人地图覆盖决策链、影响链、防线
- [ ] 项目里程碑可执行，有验收标准

### 常见错误

- 只关注技术，忽视业务和关系
- 计划过于理想化，不考虑客户实际约束
- 风险评估过于乐观
