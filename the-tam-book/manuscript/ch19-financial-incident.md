# 第 19 章　金融级事件管理

> 金融级事件同时接受三把尺子度量。三把尺子是响应时钟、监管口径和问责边界。技术处置只是其中一部分。本章解决五类操作。准备响应机制。处置金融事件。配合监管上报。完成根因分析（Root Cause Analysis，RCA）。划清定级与问责边界。本章为 How-to。通用升级与危机沟通见[第 12 章](ch12-escalation-crisis.md)，分钟级动作标准见[附录 K](appx-k-incident-emergency-drill-standard.md)。监管规则会调整，本章不替代客户合规部门或法务意见。

> 时点声明：本章的监管上报描述是通用治理框架，口径基准为 2026-10。具体义务、时限、格式和报送对象，以行业监管最新发文为准。客户制度与合同也可约定更严口径。执行前由客户合规部门确认。

## 19.1 前置条件与目标

金融事件管理必须在事前建成。事件发生后再搭机制，通常已经错过响应窗口。

| 前置条件 | 检查内容 | 缺项处理 |
| --- | --- | --- |
| 故障分级标准 | 影响范围、业务影响、时长与定级示例 | 与客户书面确认 |
| 响应时钟 | 告警、确认、定级、作战室与首次通报时限 | 按服务等级协议（SLA）和客户制度固化 |
| 升级矩阵 | 技术通道、管理通道、商务通道与联系人 | 用[模板 06](../templates/06-major-incident-communication-matrix.md)维护 |
| 预授权清单 | 扩容、切换、重启、回退等动作的授权边界 | 按[附录 T](appx-t-online-change-standard.md)确认 |
| 值班与演练 | 值班表、联系人、演练记录和能力评估 | 按[附录 I](appx-i-on-duty-standard.md)、[附录 K](appx-k-incident-emergency-drill-standard.md)核对 |
| 证据源 | 监控、日志、变更、工单、操作和通报记录 | 建立证据索引与时钟校准 |
| 沟通模板 | 首次通报、进展通报、管理层通报和恢复通报 | 按[第 12 章](ch12-escalation-crisis.md)准备 |
| 监管配合路径 | 客户合规接口、报告模板、审核流程和时限 | 与客户合规部门确认 |
| RCA 模板 | 证据、根因、防线四问和改进项 | 使用[模板 07](../templates/07-rca-template.md) |

完成标志有六项。响应有时钟。处置有授权。事实有单一版本。监管材料能倒排交付。RCA 有证据和防线分析。定级与问责有清晰边界。

| 目标 | 完成标志 | 主要证据 |
| --- | --- | --- |
| 响应及时 | 时钟动作在时限内完成 | 告警与时间线 |
| 处置可控 | 预授权动作按边界执行 | 操作、审批与复核记录 |
| 口径一致 | 对外事实由授权人签发 | 通报版本记录 |
| 监管可配合 | 材料按客户时限倒排交付 | 交付与接收记录 |
| 复盘可信 | 证据链、根因和改进项可复核 | RCA 与验证记录 |
| 定级可信 | 分级有依据，争议有记录 | 定级纪要 |

## 19.2 操作一：准备分钟级响应机制

### 19.2.1 响应时钟

下表是金融核心系统的建议基线。执行值以客户 SLA、监管口径和客户制度为准。

| 时段 | 动作 | 责任人 |
| --- | --- | --- |
| 0–1 分钟 | 告警双通道触达值班人，未接即升级 | 监控平台到值班 |
| 1–5 分钟 | 值班确认介入，启动初步定位，通知 TAM | 值班工程师 |
| 5–10 分钟 | 完成故障定级初判。故障 P2 及以上启动升级 | 值班加 TAM |
| 10–15 分钟 | 作战室就绪，角色、频道和时间线就位 | 指挥官加 TAM |
| 15 分钟内 | 发出首次客户通报，可只写已确认事实 | 联络官 |

### 19.2.2 三个成立前提

1. **告警质量**。分钟级响应需要可信告警。告警风暴会让值班人忽略关键信号。降噪规则见[第 23 章](ch23-service-model-evolution.md)。
2. **授权前置**。扩容、切换、重启和回退要预授权到岗位。危急时刻再走常规审批，机制就会失效。
3. **演练保持**。分钟级能力依靠演练维持。类型、频次和合格判定按[附录 K](appx-k-incident-emergency-drill-standard.md)执行。

### 19.2.3 准备步骤

1. 与客户确认故障分级标准、响应时钟和升级矩阵。
2. 把预授权动作、边界和双人复核要求写成清单。
3. 核对值班表、联系人和替班人，并定期实测触达。
4. 建立证据索引，标明每类证据的位置、负责人和导出方式。
5. 校准监控、日志、变更和工单系统的时间源。
6. 准备首次通报、进展通报和恢复通报模板。
7. 与客户合规部门确认监管报告路径和材料格式。
8. 每次演练后修订时钟、授权清单和升级路径。

## 19.3 操作二：处置金融级事件

### 19.3.1 处置原则

金融事件处置有三条底线。先恢复业务，再完善解释。先记录事实，再分析原因。先由授权人决策，再扩大通报范围。

### 19.3.2 操作步骤

1. **确认事实**：记录发现时间、告警来源、影响对象和已验证现象。
2. **初步定级**：按书面标准初判。争议时先按较高故障级别响应。
3. **启动作战室**：故障 P1 或影响重大时立即启动。角色参见[第 12 章](ch12-escalation-crisis.md)。
4. **执行处置**：优先使用预案和预授权动作。双人复核高风险操作。
5. **持续记录**：记录员实时维护时间线。禁止事后补记和修饰。
6. **通报客户**：按固定节奏通报。没有进展也要通报“仍在处置”。
7. **协调资源**：TAM 统一调度厂商专家，避免多头指挥。
8. **验证恢复**：业务指标恢复不等于事件关闭。按客户口径完成观察期。
9. **关闭事件**：由客户或指挥部确认关闭，保留遗留风险和观察项。

黄金 30 分钟的动作序列见[附录 K](appx-k-incident-emergency-drill-standard.md) K.5。金融值守场景见[第 18 章](ch18-major-assurance.md)。

### 19.3.3 时间线最低字段

| 字段 | 要求 |
| --- | --- |
| 时间 | 精确到分钟，使用校准时钟 |
| 来源 | 写明监控、日志、电话、会议或工单 |
| 事实 | 只写已验证现象和已执行动作 |
| 执行人 | 写明岗位，必要时写姓名 |
| 版本 | 修改留痕，不覆盖原记录 |

## 19.4 操作三：配合监管事件上报

### 19.4.1 TAM 的三件事

TAM 不决定客户是否向监管报告，也不代替客户撰写监管材料。TAM 负责三件事。

1. **知情**：了解客户所在细分领域的事件报告框架。知道红线在哪，才能提前准备材料。
2. **配合**。按客户监管时限倒排工作。提供厂商侧技术事实、时间线和影响分析。必要时提供根因说明和改进承诺。
3. **口径一致**。厂商材料、客户通报和监管报告，应使用同一套已确认事实。

### 19.4.2 倒排交付

| 客户节点 | TAM 动作 |
| --- | --- |
| 客户确认需要报告 | 立即指定厂商材料负责人 |
| 客户给出报告时限 | 从报送时点倒排厂商交付时点 |
| 客户要求 24 小时内报告 | 厂商初稿建议 4–6 小时内送达 |
| 客户内部审核 | TAM 留人答复追问并修订材料 |
| 报送完成 | 归档版本、时间和接收人 |

### 19.4.3 厂商材料清单

| 材料 | 内容要求 |
| --- | --- |
| 事实包 | 发现、影响、处置、恢复和当前状态 |
| 时间线 | 多源互证，精确到分钟，标注来源 |
| 影响分析 | 业务范围、持续时长、客户影响和量化口径 |
| 技术分析 | 已验证原因、初步判断和待核实项 |
| 改进承诺 | 止血措施、治本措施、Owner 和期限 |
| 证据索引 | 日志、监控、变更、工单和通报记录位置 |

### 19.4.4 口径三纪律

1. **单一事实版本**。对外技术事实由事件指挥官或授权人签发。
2. **时间线零修饰**。以实时记录为准。与系统日志不一致会变成诚信问题。
3. **未查明不给结论**。对外使用“初步判断”或“正在核实”。不提供可能进入监管报告的推测。

## 19.5 操作四：完成金融级 RCA

### 19.5.1 金融级 RCA 的四个增量

一般 RCA 回答“什么原因、怎么修”。金融级 RCA 还要回答三个问题。防线为什么没拦住？同类风险还在哪里？证据能否经得起审计？

| 增量要求 | 做什么 | 证据标准 |
| --- | --- | --- |
| 证据链完整 | 串联告警、变更、操作、日志和处置 | 多源时间对齐，可回放 |
| 防线分析 | 逐层问预防、发现、恢复和缺口 | 每层失效单独列改进项 |
| 同类风险扫描 | 扫描同类组件、配置、操作和依赖 | 结果进入风险登记册 |
| 改进项可验证 | 写明验证方式、Owner 和期限 | 验收证据可复查 |

### 19.5.2 操作步骤

1. 冻结时间线版本，收集监控、日志、变更、工单和通报记录。
2. 核对各系统时间源。时间不一致时，先建立换算关系。
3. 区分近因、根因和促成因素。只写有证据的结论。
4. 完成 5Why 分析，追到可消除或可控的层级。
5. 回答防线四问：为何没预防、没早发现、恢复慢、缺口未入册。
6. 扫描同类风险，登记新风险和需要观察的项。
7. 每条改进项写明止血或治本属性、验证方式和期限。
8. 按客户要求分发。含己方责任的内容不得删节后选择性送达。
9. 到期验证改进项，记录证据。未验证视同未闭环。

RCA 使用[模板 07](../templates/07-rca-template.md)。复盘组织方法见[附录 R](appx-r-problem-retrospective-standard.md)。

### 19.5.3 时限基线

| 事项 | 建议时限 | 说明 |
| --- | --- | --- |
| 故障 P1 初步 RCA | 48 小时内 | 先交付事实包、时间线和初步判断 |
| 故障 P1 正式 RCA | 5 个工作日内 | 以[附录 K](appx-k-incident-emergency-drill-standard.md)和客户制度为准 |
| 故障 P2 正式 RCA | 5 个工作日内 | 复杂事件可申请延期并说明原因 |
| 监管配合材料 | 按客户报送时限倒排 | 优先于内部 RCA 周期 |

## 19.6 操作五：划清定级与问责边界

### 19.6.1 定级三原则

1. **标准先于事件**。分级标准在事件前书面约定。标准应覆盖影响范围、业务影响和持续时间。
2. **就高不就低**。定级争议时先按较高故障级别响应。事后可依据证据复核下调。
3. **定级与问责解耦**。定级描述影响。问责认定责任。两者挂钩会激励瞒报。

### 19.6.2 操作步骤

1. 读取书面分级标准，不使用临时口径。
2. 收集影响范围、业务结果、持续时间和恢复证据。
3. 由授权角色初判故障级别，记录依据。
4. 有争议时先按高级别响应，同时保留异议。
5. 事实稳定后复核定级。下调必须写出证据和批准人。
6. 问责分析回到流程缺陷，不停在个人失误。
7. TAM 提供事实与证据，不主导客户定责。

### 19.6.3 问责句式

金融级问责有一个标准句式。人在什么流程缺陷下，犯了什么错误。只写“个人操作失误”的结论，通常无法防止复发。流程缺陷包括无流程、流程未执行、流程有缺陷和授权不清。这四类要分开定性。

## 19.7 验收标准

| 验收项 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 响应时钟 | 时钟与客户 SLA 一致，值班能复述 | 抽问与演练记录 |
| 预授权 | 清单有效，动作有边界和复核 | 核对授权与操作记录 |
| 事件时间线 | 实时记录、来源清楚、版本留痕 | 抽查最近事件 |
| 首次通报 | 达到约定时限，只含已确认事实 | 核对通报版本 |
| 监管配合 | 材料按时倒排交付，版本可追溯 | 核对交付记录 |
| 口径一致 | 客户、监管和厂商材料事实一致 | 对照三套材料 |
| RCA 证据 | 多源时间对齐，结论有证据 | 抽查[模板 07](../templates/07-rca-template.md) |
| 防线分析 | 四问逐层回答，改进项独立 | 核对 RCA 评审 |
| 同类扫描 | 扫描结果进入风险登记册 | 核对[模板 09](../templates/09-risk-register.md) |
| 定级问责 | 标准前置，定级与问责分离 | 核对定级纪要 |

关键项包括响应时钟、时间线、监管口径一致和防线分析。任一关键项未通过，不得视为金融级事件管理合格。

## 19.8 执行故障排查

| 症状 | 常见原因 | 处理动作 |
| --- | --- | --- |
| 告警无人响应 | 触达方式单一或值班表过期 | 改双通道并实测联系人 |
| 定级反复变化 | 标准不清或受问责压力 | 回到书面标准，先高后复核 |
| 首次通报迟到 | 等根因或授权不清 | 通报与排查并行，先发已确认事实 |
| 时间线对不上 | 时钟未校准或事后补记 | 建立换算关系，恢复实时记录 |
| 多人对外口径不一 | 无授权发声人或版本混乱 | 收口到联络官，登记版本 |
| 监管材料迟交 | 未倒排或证据分散 | 建材料清单和证据索引 |
| RCA 只有技术原因 | 缺防线分析和业务视角 | 补防线四问和管理复盘 |
| 改进项不闭环 | 无验证方式或无期限 | 进台账，到期复验 |
| 团队隐瞒定级 | 问责与定级挂钩 | 重申解耦原则，问责到流程 |

反复出现的问题进入复盘流程。

## 19.9 常见误区

1. **先查原因，后做通报**。等根因清楚再通报，会把分钟级机制变成分钟级静默。
2. **为躲上报压低定级**。短期规避检查，长期会变成瞒报问题。
3. **把 RCA 写成技术作文**。只有技术根因，没有防线分析和可验证改进项。
4. **把问责当定级**。为了减少问责而压低级别，会破坏事件数据的真实性。
5. **把证据整理留到事后**。事后补记不能还原处置过程，也无法通过审计。
6. **把监管材料当厂商免责文件**。选择性删除己方责任，会破坏客户信任。

## 19.10 执行检查清单

- [ ] 响应时钟与客户 SLA 和监管口径书面一致
- [ ] 值班、升级和监管配合路径近期实测过
- [ ] 常见处置动作有预授权边界和双人复核
- [ ] 证据索引建立，关键系统时间源校准
- [ ] 最近事件时间线实时记录且版本留痕
- [ ] 首次通报按时发出，只包含已确认事实
- [ ] 客户合规部门确认过报告路径和材料格式
- [ ] 厂商监管配合材料可在约定时限内交付
- [ ] 最近故障 P2 及以上事件完成金融级 RCA
- [ ] RCA 包含防线四问和同类风险扫描
- [ ] 改进项有 Owner、期限和验证证据
- [ ] 定级标准前置，定级与问责解耦

---

**本章要点回顾**

1. 金融级事件接受时钟、监管和问责三把尺子度量。技术处置只是其中一部分。
2. 响应时钟要有告警质量、预授权和演练保持。缺一项就只是纸面机制。
3. 事件处置先恢复业务，实时记录事实，按固定节奏通报。
4. 监管配合做到知情、配合和口径一致。厂商材料按客户报送时限倒排交付。
5. 金融级 RCA 增加证据链、防线分析、同类扫描和可验证改进项。
6. 定级标准先于事件存在。争议时先高后复核，定级与问责解耦。
7. TAM 提供事实和证据，不主导客户定责。问责应追到流程缺陷。
