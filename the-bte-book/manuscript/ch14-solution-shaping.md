# 第 14 章　方案塑形与 SA 协同

> 方案不是 SA 一个人的作品。BTE 要把商业约束、客户否决点、交付边界带进方案，避免“技术正确、商业不可行”。本章给六个动作：输约束、定标准、参评审、守可运营、冻基线、交交付。

## 14.1 前置条件与目标

| 前置条件 | 检查内容 | 缺项处理 |
| --- | --- | --- |
| 需求基线 | 场景、五要素、优先级已签认 | 先回第 12 章 |
| 商业约束 | 预算、时间、合规、竞争 | 先补商机卡 |
| SA 接口 | 方案负责人已定 | 先定协作 |
| 交付接口 | TAM 或交付代表已定 | 先约评审 |
| 评审机制 | 技术、可运营、商务三关 | 先定流程 |

完成标志有四项：约束已输入；评估标准已定；评审有结论；基线已冻结。

| 目标 | 完成标志 | 主要证据 |
| --- | --- | --- |
| 约束清楚 | 商业约束写进方案输入 | 方案输入表 |
| 标准清楚 | 客户评估标准可量化 | 评估标准表 |
| 评审有效 | 三关有结论与签字 | 评审记录 |
| 基线可交 | 方案版本冻结 | 基线页 |

## 14.2 操作一：输入商业约束

### 步骤

1. 列四类约束：预算上限、时间窗、合规要求、竞争位置；
2. 每类写“硬约束”或“可谈”；
3. 硬约束写违反后果；
4. 把约束交给 SA，作为方案设计的输入；
5. 约束变化时 24 小时内同步 SA。

### 预期结果

SA 知道方案必须在什么框里设计，不做无效方案。

### 常见错误

- 只给需求，不给预算；
- 时间窗不说，方案排期脱离客户节奏；
- 约束变化不通知，方案白做。

## 14.3 操作二：定义评估标准

### 步骤

1. 与客户确认评估维度：功能、性能、成本、风险、服务、合规；
2. 每个维度写权重与判据；
3. 判据要可验证，不写“体验好”；
4. 评估标准与招标评分点对齐；
5. 标准确认后，作为方案自评依据。

### 预期结果

方案知道“按什么标准评判”，不靠感觉。

### 常见错误

- 只按厂商能力写标准；
- 权重不确认，评标时吃亏；
- 判据不可验证，客户各说各话。

## 14.4 操作三：参与方案评审

### 步骤

1. 参加技术评审，带商业约束与客户否决点；
2. 参加可运营评审，带 TAM 的一票关注项；
3. 参加商务评审，带成本与报价边界；
4. 每关只问三个问题：能不能交付、客户认不认、公司赚不赚；
5. 评审结论三选一：通过、带条件、退回。

### 预期结果

方案在技术、运营、商业三方面都过一遍。

### 常见错误

- BTE 不参加评审，方案脱离商业；
- 评审只看技术，不看可运营；
- 带条件通过的条件没人跟踪。

## 14.5 操作四：守住可运营性

### 步骤

1. 请 TAM 按四项检查：监控、变更、故障处置、容量；
2. 任一项不过，方案退回或带条件；
3. 条件写进风险清单，指定 Owner 与期限；
4. 不因赢单压力绕过可运营评审；
5. 客户知情的例外，要书面确认。

### 预期结果

方案上线后能运维，不把坑留给交付。

### 常见错误

- 为赢单压配置；
- 绕过 TAM 评审；
- 例外只口头说，交付期不认。

## 14.6 操作五：冻结方案基线

### 步骤

1. 冻结架构图、配置基线、容量假设、POC 记录；
2. 基线版本号与日期写清；
3. 客户与内部各留一份；
4. 基线变更走书面，口头不算；
5. 基线作为报价与合同的输入。

### 预期结果

方案有版本，后续变更可追溯。

### 常见错误

- 基线只在 SA 电脑里；
- 变更不留痕；
- 报价用了旧基线。

## 14.7 操作六：交接给交付

### 步骤

1. 把方案基线、承诺清单、风险清单交给交付与 TAM；
2. 开交接会，逐条过三件套；
3. 标出方案假设与未决项；
4. 约定伴随期支持方式；
5. 交接会纪要双方签认。

### 预期结果

交付知道方案从哪来，承诺有哪些，风险在哪。

### 常见错误

- 只发文档，不开会；
- 假设不交底；
- 交接后 BTE 失联。

## 14.8 验收标准

| 验收项 | 通过标准 | 验证方式 |
| --- | --- | --- |
| 约束输入 | 四类约束已交 SA | 核对方案输入表 |
| 标准可量化 | 评估维度有权重与判据 | 核对标准表 |
| 三关评审 | 技术、可运营、商务有结论 | 核对评审记录 |
| 可运营守住 | 四项检查有结论 | 核对 TAM 意见 |
| 基线冻结 | 版本、日期、范围清楚 | 核对基线页 |
| 交接完整 | 三件套逐条过 | 核对交接纪要 |

关键项是约束输入、可运营守住、交接完整。任一未过，方案塑形不算合格。

## 14.9 执行故障排查

| 症状 | 常见原因 | 处理动作 |
| --- | --- | --- |
| 方案很全，客户不买 | 商业约束没输入 | 补预算、时间、竞争约束 |
| 评标得分低 | 评估标准没对齐 | 按评分点重排方案 |
| 上线后运维困难 | 绕过可运营评审 | 补 TAM 四项检查 |
| 报价与方案对不上 | 基线没冻结 | 用冻结基线重算 |
| 交付不认承诺 | 交接走过场 | 重开交接会逐条过 |
| 变更失控 | 基线变更无记录 | 补书面变更流程 |

## 14.10 执行检查清单

- [ ] 四类商业约束已输入方案
- [ ] 评估标准有维度、权重、判据
- [ ] 技术、可运营、商务三关评审完成
- [ ] TAM 四项可运营检查有结论
- [ ] 方案基线已冻结并编号
- [ ] 三件套已逐条交接
- [ ] 方案假设与未决项已交底
- [ ] 伴随期支持方式已约定

---

**本章要点回顾**

1. BTE 不画架构，但要给方案输入商业约束。
2. 评估标准要可量化，并与评分点对齐。
3. 三关评审：技术、可运营、商务。可运营一票不能绕。
4. 方案基线要冻结，报价与合同都靠它。
5. 交接三件套逐条过，假设与未决项要交底。
6. 方案失败常常不是技术错，是商业约束没进方案。
